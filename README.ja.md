# Threads 爆発レーダー · リアルタイムキーワード監視

Threads 上で、あなたが追っているキーワードに関連する公開投稿を監視し、リアルタイムでランキングにまとめます。

**サードパーティ依存ゼロ、Python 標準ライブラリのみ**——Python さえ入っていればすぐ動きます。`pip install` は不要です。

![License](https://img.shields.io/badge/License-MIT-blue.svg)
![Python](https://img.shields.io/badge/Python-3.10%2B-3776AB.svg)
![Dependencies](https://img.shields.io/badge/dependencies-none-brightgreen.svg)
![Platform](https://img.shields.io/badge/platform-Windows%20%7C%20macOS%20%7C%20Linux-lightgrey.svg)

3 つのビューが 3 つの異なる問いに答えます：

| ビュー | 答える問い |
|---|---|
| **キーワードレーダー** | どの**投稿**が今バズっているか |
| **競合モニタリング** | 誰が**継続的に**ヒットを出しているか（アカウント単位の集約＋継続度の階層） |
| **ウォッチリスト** | **自分が追っている人**の中で、誰が新しく投稿したか |

どのビューでも、現在の絞り込み結果をそのまま CSV に書き出せます（Excel でそのまま開けます）。

### 主な特徴

- **本当にリアルタイム**：常駐プロセスが一定間隔で収集し、ページは SSE で更新を受け取ります。収集が終わった瞬間にランキングが更新され、手動でクリックする必要はありません
- **4 つのエンゲージメント指標が揃っている**：いいね / 返信 / リポスト / 引用。公式 API ではこれらを取得できません
- **サムネイル付き**：リスト / カード / 詳細の 3 か所で画像を表示し、各投稿がテキストのみ / 単一画像 / カルーセル / 動画のどれかを明示。バズ判定のために 1 件ずつ開く必要はありません
- **上昇速度を独立した列に**：`インタラクション / 時間`。「累計が多い」ではなく「今伸びている」ものが見えます
- **エンゲージメント成長曲線**：収集のたびにスナップショットを記録するので、投稿の伸び方を詳細ドロワーで確認できます
- **チャネル健全性チェック＋サーキットブレーカー**：失敗は実際の原因ごとに分類され、空のサイクルが続けばブロックされた出口を叩き続けずに監視を停止します
- **依存ゼロ**：`urllib` / `sqlite3` / `http.server` / `threading` のみ。長時間の稼働でも環境の変化で壊れません
- **3 段階のレスポンシブ**：デスクトップ / タブレット / モバイル。54 通りの幅×ビューの組み合わせで横スクロールが発生しないことを実測済み

## クイックスタート

**Python 3.10 以上**が必要です。`pip install` は不要（サードパーティ依存ゼロ）。

```
start.bat をダブルクリック
```

または：

```bash
python server.py
```

その後、ブラウザで **http://127.0.0.1:8650** を開きます。

起動時に第 1 サイクルの収集がすぐに走り、以降は設定した間隔で自動的に繰り返します。

### まず threads.com に接続できるか確認

ここが**唯一つまずきやすいポイント**です。プログラムは Python 標準ライブラリの `urllib` で取得し、
`urllib` はシステムの `http_proxy` / `https_proxy` 環境変数を自動的に読みます。
そのため、直結できない場合は以下のいずれかの方法でプロキシを設定してください。

**方法 1：`.env` に書く**（推奨。プロジェクトと一緒に持ち運べます）

```bash
cp .env.example .env          # Windows: copy .env.example .env
```

次に `.env` を編集し、コメントを外して自分のポートに変更します：

```env
http_proxy=http://127.0.0.1:7890
https_proxy=http://127.0.0.1:7890
```

**方法 2：システム環境変数に設定する**（Windows コマンドラインで一時的に有効）

```bat
set http_proxy=http://127.0.0.1:7890
set https_proxy=http://127.0.0.1:7890
```

> ポートの探し方：Clash / v2rayN などのクライアントの「HTTP ポート」または「混合ポート」。
> **`socks5://` は書かないでください**——`urllib` は socks プロキシに対応していないため、HTTP ポートが必須です。

設定後は、画面右上の **チャネル自己診断**（`POST /api/probe`）で検証できます。
コマンドラインで確認する場合：

```bash
python -c "from collector import probe_channel; print(probe_channel())"
```

> ⚠️ プロキシは収集時に必ず起動している必要があります。切るとチャネルは 502（`proxy_tunnel_502`）を返します。
> 切り分けはまず `baidu.com` / `api.github.com` と比較してください。この 2 つが通って `threads.com`
> だけ通らない → 出口が Meta のレート制限対象（頻度を下げると約 20 分で回復）。3 つとも通らない → プロキシ自体の障害です。
> チャネルの状態と失敗理由は画面上部の警告バーに表示されます。

## 配布 / 他の人に使ってもらう

**このプロジェクトは「自分専用のリアルタイム監視コンソール」であり、公開サービスではありません。**既定では `127.0.0.1` のみをリッスンします。
他の人に使ってもらう最も簡単な方法は、相手に clone して自分で動かしてもらうことです。

```
git clone https://github.com/BaYue-SYJ/threads-ai-radar.git
cd threads-ai-radar
# プロキシを設定（上の節を参照）
start.bat            # または python server.py
```

3 点だけ注意：

1. **依存のインストールは不要**です。Python さえ入っていれば動きます。データベース `data/radar.db` は初回起動時に自動作成されます。
2. **各マシンがそれぞれのデータを収集します**。このプログラムにはアカウント機能もデータ同期もありません。
   2 人で同じランキングを見たい場合は、同じマシンに接続してください（次項参照）。
3. **公開ネットワークに野ざらしにしないでください**。HTTP サービスには認証が一切なく、
   ポートに到達できる人は誰でもキーワードとウォッチリストを変更できます。LAN で共有する場合も、内部アドレスにのみバインドしてください：

   ```env
   RADAR_HOST=0.0.0.0        # または .env で具体的な LAN IP を指定（例: 192.168.1.10）
   ```

   そのうえでファイアウォールで送信元 IP を制限してください。**公開側へのポート転送はしないでください。**

### `tools/` ディレクトリについて（任意）

`tools/` にあるのは、私がこのプロジェクトを改修する際に使った**リグレッションテストスクリプト**です。実行には Node が別途必要です：

| スクリプト | 役割 | 依存 |
|---|---|---|
| `check_e2e.cjs` | E2E リグレッション：ウォッチリストの追加/削除、スター、双方向ジャンプ、CSV 書き出しを一通り（39 アサーション） | puppeteer-core |
| `check_watch.cjs` | レスポンシブ走査：18 幅 × 3 ビュー = 54 通りで横スクロールと JS エラーを検査 | puppeteer-core |
| `shots3.cjs` | 3 ビューの自動スクリーンショット（デスクトップ 1440 / タブレット 1024 / モバイル 390） | puppeteer-core |
| `scan_broken_modules.cjs` | `node_modules` 内の「パッケージはあるがエントリファイルが消えた」壊れたパッケージを検出 | **なし** |

**ツールとして使うだけなら、このディレクトリは気にしなくて構いません。** リグレッションを走らせる場合：

```bash
npm i -D puppeteer-core
node tools/check_watch.cjs        # サーバーを先に起動しておく
```

スクリプトは Chrome を自動検出します。見つからない場合は `CHROME_PATH` / `PUPPETEER_PATH` で指定してください。

## どうやってデータを取得しているか

これがプロジェクト全体で最も重要な点なので、最初に明確にしておきます。

**公式 Threads API は使えません：** `keyword_search` は Meta の App Review 通過が必要で、未承認のうちは自分が投稿したものしか返しません。しかもレスポンスに**いいね / 返信 / リポスト / 引用の 4 つの数値がそもそも含まれていません**。エンゲージメントが取れない「バズレーダー」は存在しないのと同じです。

**実際に採用しているのは：Googlebot UA ＋ サーバーサイドレンダリング。**

| リクエスト方法 | 返ってくる内容 |
|---|---|
| 通常のブラウザ UA | 約 275KB の SPA の空殻。**投稿データは一切なし** |
| `Googlebot` UA | **1.0〜1.9MB の完全な SSR ページ**。投稿データがインライン JSON として格納 |

ログイン不要、OAuth 不要、App Review 不要、コストゼロ。4 つのエンゲージメント指標すべてが取得できます。

### フィールド位置（コードを触る時に最もハマりやすい罠）

4 つの指標は**同じ階層にありません**：

| フィールド | 位置 |
|---|---|
| `like_count` | 投稿オブジェクトの**最上位** |
| `direct_reply_count` | `text_post_app_info` の中。**`reply_count` という名前ではない点に注意** |
| `repost_count` | `text_post_app_info` の中 |
| `quote_count` | `text_post_app_info` の中 |

あるオブジェクトが投稿かどうかを判定するには、条件に `code` + `like_count` + `text_post_app_info` を**同時に**含める必要があります。
最初の 2 つだけだと**外側で止まって下に降りず**、残り 3 つのフィールドがすべて 0 として読まれます——これは開発中に実際にハマった罠です。

## キーワードの書き方

`keywords.txt` を編集するか、画面上部の「監視キーワード」パネルから直接追加・削除します。

```
[モデル]                   ← 角括弧はグループ。画面上のカテゴリとしてそのまま使われます
ChatGPT | GPT | chatgpt   ← 縦線は同義語の区切り
AI prompt                 ← 空白 = AND
```

- **空白 = AND**：`AI prompt` は本文に AI と prompt の両方が必要
- **縦線 = OR**：`ChatGPT | GPT` はいずれかに一致すれば関連と判定。
  **検索に使うのは最初の書き方だけ**で、後ろは判定にのみ使われます。多くの投稿はフルネームではなく `GPT` とだけ書くので、同義語を足さないと取りこぼします。
- ハッシュタグの連結にも自動対応：`#aiprompt` も `AI prompt` に一致します
- `ai` のような短い語には近似の語境界マッチを使うので、`said` / `available` を誤って拾いません

## 関連性フィルタ

Threads の検索は**意味ベースの召回**であり、「本文にその語が含まれる」召回ではありません。実測では `AI prompt` で検索すると、インドネシア語のエンゲージ稼ぎ投稿や、AI 規制を語る政治家の投稿（11,168 いいねで首位）まで返ってきます。

そのため、各収集サイクル後に投稿へ判定を付けます：

| 判定 | 意味 |
|---|---|
| **関連** | 本文がキーワードフレーズ、または有効語すべて、または同義語に一致 |
| **無関係** | 検索で拾われたが、本文はキーワードと無関係 |
| **ブロック** | `blocklist.txt` のノイズ語に一致 |

画面上の「**関連のみ表示**」スイッチで後ろ 2 種を表示するか制御できます（既定はオン）。

**関連率は構造的に低く、実測で約 4%**——これは Threads 検索の性質であり、バグではありません。
本機で累計 16,710 件を収集し、そのうち関連は 730 件（**4.4%**、2026-09-15 時点）。
極端な例：`Nano Banana` で 64 件収集し、"banana" を含むものは **0 件**——
すべてインドネシア語の「nano KOL」マーケティング投稿で、フィルタが正しく全て弾いています。

> 関連率が低い＝役に立たない、ではありません。弾いているのは意味的なノイズで、残るのは本当のヒットです。
> カバレッジを上げたいなら、フィルタを緩めるよりキーワードとバリアントを増やす方が効果的です。

キーワードやブロック語を変更した後、既存データを再判定したい場合（再取得は不要）：

```bash
python refilter.py
```

## 取得バリアント（実質的なページ送り）

Threads 検索ページの `serp_type` パラメータは**異なるバッチ**の結果を返します。複数のバリアントを取ってマージ・重複排除すると、
ページ送りと同等の効果が得られます——これは内部 GraphQL でカーソルを取るより信頼できます（実測では GraphQL チャネルは実ブラウザの
セッション cookie + csrf が必要で、直接 POST しても HTML の外殻しか返りません。しかも doc_id はローテーションします）。

**⚠️ バリアントの選択は「関連投稿の産出」で見るべきで、「生の件数」では判断できません——両者の差は極めて大きい。**

各バリアントが新たに生む**関連投稿**数（base を基準に実測）：

| キーワード | base | recent | top | tag | **profile** | **default** |
|---|---|---|---|---|---|---|
| ChatGPT | 15 | +0 | +0 | +0 | **+17** | +9 |
| Nano Banana | 3 | +0 | +2 | +1 | **+13** | +7 |
| AI prompt | 21 | +6 | +0 | +1 | +0 | **+10** |

`recent` は生の件数が大きく増えますが、**そのほとんどが意味的なノイズ**です。本当の価値は `profile` と `default` にあります。
私は当初、生の件数で `base,recent,top` を選び、結果として最も弱い 2 つのバリアントを選んでいました——関連投稿の産出で選び直して初めて実際の効果が得られました。

3 バリアントの実測効果：

| | 単一バリアント | 3 バリアント | 改善 |
|---|---|---|---|
| 収録総数 | 980 | **3,865** | 3.9× |
| **関連投稿** | 136 | **415** | **3.1×** |
| カバーアカウント | 941 | 3,562 | 3.8× |
| 1 サイクルの所要時間 | 約 2 分 | 約 7 分 | 3.5× |

### ⚠️ バリアント数はブロックリスクに直結します（実測で経験済み）

3 バリアント × 19 キーワード = **1 サイクル 57 リクエスト**。3 サイクル走らせたところ、`threads.com` が本機の出口に対して返し始めました：

```
urllib.error.URLError: Tunnel connection failed: 502 Bad Gateway
```

同時に `baidu.com`、`api.github.com` は 200 のまま——つまり**プロキシの障害でも Threads の障害でもなく**、出口 IP が Meta のレート制限を受けたということです。約 20 分で自然回復しました。

結論：**長時間の稼働ではバリアントは 2 つまで**（既定は `base,profile`）とし、間隔は 30 分以上に伸ばしてください。制限後の唯一有効な回復手段は負荷を下げて一定時間止めることです。しつこいリトライはブロックを長引かせるだけです。

> この種の問題は必ずチャネルを分けて検証してください。`baidu.com` / `api.github.com` と比較することで、「プロキシ全体の障害」と「特定ターゲットへのレート制限」を切り分けられます。

## リアルタイム監視の仕組み

`server.py` は起動時にプロセス内でバックグラウンドのスケジューラスレッドを立ち上げます：

- 一定間隔（既定 15 分）で全キーワードを巡回収集
- キーワード間に 1.8〜4.2 秒の**ランダムなゆらぎ**を挿入し、一定のリズムでレート制限を誘発するのを回避
- ページは **SSE**（`/api/stream`）で更新を受け取り、2 秒ごとに状態を同期。収集完了時に即座にランキングを更新
- 収集のたびに `snapshots` テーブルへエンゲージメント数のスナップショットを書き込み、詳細ドロワーで伸び率の曲線が見られます

画面で確認できるもの：

- ナビゲーションバーの状態ドット：**監視中 / 収集中 / 一時停止 / チャネル異常**
- 次回収集までの**カウントダウン**
- 収集の進捗バー `7/19 · Midjourney`
- スクロールする収集ログ（異常警告を含む）
- 新規登録された投稿の **NEW** バッジ

### レスポンシブ

3 つのビューすべてがデスクトップ / タブレット / モバイルに対応。**18 幅（390〜1680px）× 3 ビュー = 54 通りの組み合わせで横スクロールが発生しないことを実測済み**：

<p align="center">
  <img src="docs/mobile.png" width="380" alt="モバイル版キーワードレーダー">
</p>

| ブレークポイント | ナビゲーションバー | 競合テーブル | ウォッチリストテーブル |
|---|---|---|---|
| ≥1181px | 1 行 | 全 11 列 | 全列 |
| 1081〜1180px | 余白を詰める | ヒット率 / 平均インタラクション / 最高スコアを非表示（ヒット率は投稿数から算出可能） | 主な領域を非表示（幅をメモに譲る） |
| ≤1080px | 操作部を 2 行目へ | 同上 | 同上 |
| ≤860px | 同上 | 既定で**カード表示**に切替。手動でテーブルにした場合はコンテナ内で横スクロール可（列を黙って削らない） | 同上。フォームは 1 行ずつの積み重ねに |

> ハマり記録：3 つ目のタブ（ウォッチリスト）を追加した後、ナビゲーションバーの最小コンテンツ幅が **1078px** に増えました。
> 元は 860px のブレークポイントでしか折り返しておらず、その結果 **1024px で右側のコントロールが画面外に 54px はみ出しました**——
> デスクトップもモバイルも正常で、中間のこの範囲だけが壊れるため、見落としやすいのです。
> 現在は 1 行に収まらなければ全体を下段に移す方式で、余白を詰め続けることはしません（詰めるとボタンが団子になります）。
>
> もう一つの罠：**`getBoundingClientRect().right > clientWidth` によるはみ出し検出は、閉じているドロワーをすべてはみ出しとして数えてしまいます**
> ——ドロワーは `translateX(101%)` で画面外に退避しているためです。検出スクリプトでドロワーを除外しないと、どの幅でも誤検知します。
> より信頼できる判定は `documentElement.scrollWidth > clientWidth` です。

### 健全性チェックとチャネル自己診断

取得のたびに「レスポンスサイズが 400KB 以上、かつ 5 件以上の投稿を解析できたか」を検証し、満たなければ異常とします。

ただしサイズ検査だけでは不十分です——**「取得はできたがページにデータがない」と「経路自体が通っていない」は別物**で、前者は取得器を再起動すれば済みますが、
後者はしつこいリトライがレート制限を悪化させるだけです。そこで失敗は具体的な原因に分類されます：

| reason | 意味 | 対処 |
|---|---|---|
| `proxy_tunnel_502` | プロキシトンネル 502、出口が拒否 | 頻度を下げる＋一定時間停止 |
| `rate_limited` | HTTP 429 でレート制限 | バリアント数を減らし間隔を伸ばす |
| `connect_timeout` | 直結が遮断 | 利用可能なプロキシ経由にする |
| `tls_reset` | TLS が中間機器にリセット | 経路を変更 |
| `gateway` | 上流 5xx | 通常は自然回復 |
| `empty_shell` | ページは取得できたが SSR がない | UA が降格。`RADAR_USER_AGENT` を変更していないか確認 |

ナビゲーションバーの「**自己診断**」を押すか `/api/probe` を呼ぶと、**1 リクエストだけ**送ってチャネル状態を素早く判定します。サイクル全体の完了を待つ必要はありません。

![チャネル異常の警告バー](docs/channel-alert.png)

上の画像は出口がレート制限を受けた際の実際の画面です。上部の赤いバーが**具体的な原因**（`proxy_tunnel_502`）と
**実行可能な対処**（一定時間待って再試行、またはバリアント数を減らす）を示します。ログに「ページ異常」の 1 行を残すだけではありません。
ナビゲーションバーの状態ドットも同時に「チャネル異常」へ変わります。

### サーキットブレーカー

**1 サイクルが完全に空**（19 キーワードで 1 件も取得できない）になると、個別キーワードのデータ不足ではなくチャネル障害と判断します。
これが **3 サイクル**続くと**監視を自動停止**し、ログに理由を残します——ブロックされた出口を一定間隔で叩き続けるのを避けるためです。

画面上部に赤い警告バーが出て理由と対処を示します。ログに「ページ異常」の 1 行を残すだけではありません。

### サイクル全体のウォッチドッグ

1 サイクルの収集には**厳格な時間上限**があります（`RADAR_CYCLE_MAX_SECONDS`、既定 1800 秒 = 30 分）。
時間切れになるとそのサイクルを中断し、どのキーワードで止まったか、なぜ止まったかをログに書きます。

なぜ必要か：**ノート PC のスリープは収集スレッドを丸ごと凍結させます**。実測では 7 番目のキーワードを処理した後にマシンがスリープし、
スレッドが **15.5 時間**その場で戻ってきませんでした（スリープをまたぐと単一リクエストの socket タイムアウトが効かないことがあります）。
その間、次のサイクルの収集はずっとブロックされていました。ウォッチドッグは各キーワードの開始前にタイムアウトを確認し、復帰後すぐに終了処理に入るので、
次のサイクルが正常に始められます。

途中で中断した場合、`keywords_done` は**実際に完走した件数**をそのまま記録します（例：`9/19`）。
「今回は全件完了」と偽ることはありません。

### 中断した残レコードの自動処理

プロセスが強制終了（またはウォッチドッグによる中断）されると、収集レコードは `running` のまま残ります。起動時に自動で走査し、
該当レコードを `error / プロセス中断、このサイクルは未完了` に更新します——そうしないと画面が「収集中」のままになり、
ツールが固まったように見えてしまいます。

## 競合 / 同業モニタリング

キーワードランキングが答えるのは「**どの投稿がバズったか**」。同業ランキングが答えるのは「**誰が継続的にヒットを出しているか**」です。
後者は著者単位の集約が必要で、ここがこのプロジェクトの真の差別化点です——競合分析で見るべきは人と方法論であり、単一の投稿ではありません。

画面上部の 2 つ目のタブ「**競合モニタリング**」で、関連投稿を著者単位に集約します：

- **階層**：継続度による自動ラベリング。これが監視対象を選ぶ判断材料になります

  | 階層 | 条件 | 意味 |
  |---|---|---|
  | 主要監視 | 投稿 ≥ 3 かつ ヒット ≥ 2 | 方法論が安定。長期的に追う価値あり |
  | 継続産出 | 投稿 ≥ 2 | 安定した産出がある |
  | 単発ヒット | 投稿 = 1 かつ ヒット ≥ 1 | まぐれの可能性 |
  | 散発出現 | それ以外 | 一度だけ出現 |

  （ヒット = 単一投稿のインタラクション合計 ≥ 500。閾値は `store.HIT_THRESHOLD`）

- **各行に表示**：関連投稿数、ヒット数、ヒット率、総インタラクション、1 投稿あたり平均、最高スコア、主な領域、最近の活動
- **任意のアカウントをクリック**でドロワーを開く：階層、投稿ペース（約 N 投稿/週）、主な領域、一致したキーワード、そのアカウントの全関連投稿
- **並び替え**：ヒット数 / 関連投稿数 / 総インタラクション / 1 投稿平均 / ヒット率 / 最高スコア / 最高いいね / 今回の新規

### 「継続度」フィルタが必須な理由

データ量が少ないうちは、ほとんどのアカウントが 1 回しか出現しません。初回の 391 著者の実測：

```
投稿数 ≥ 1：391        投稿数 ≥ 2：14        投稿数 ≥ 3：5
階層分布：主要監視 1 / 継続産出 13 / 単発ヒット 50 / 散発出現 327
```

**アカウントの 96% が「一度だけの出現」**です。ヒット数でそのまま並べると、ランキングは単発の著者で埋まり、誰を長期的に追うべきか全く分かりません。
そのため「継続産出のみ（≥2 投稿）」スイッチを既定で用意し、階層ごとに既定の並び替え項目を設定しています。

画面上部にはサンプルの厚みが表示され、「継続産出」の人数が少ないのは収集サイクルがまだ足りないからであり、
機能が壊れているからではないと分かるようにしています。**何度も回して初めてこのランキングは情報量を持ちます**——これがアカウント軸が時間の蓄積を必要とする理由です。

## ウォッチリスト

同業ランキングは「サイト全体を走査した順位」、ウォッチリストは「**自分で囲って追う人**」です。この 2 つは別の画面が必要です：
前者は網羅性と並び替えによる法則の発見が、後者は短さと「誰が新しく投稿したか」の一目瞭然さが求められます。

3 つ目のタブ「**ウォッチリスト**」。3 つの入口から追加できます：

- 競合モニタリング画面の各行/各カード左側の **☆** でワンクリック登録（テーブル・カード両表示に対応）
- ウォッチリスト画面の上部の入力欄。`@xxx`、`xxx/`、プロフィールや投稿の URL をそのまま貼り付け可能
- `watchlist.txt` を直接編集。形式は `アカウント | メモ`。再起動時に自動で読み込まれます

登録後：

- **新着投稿がある人が最上位**に来て、`+N` の青いバッジが付きます。上部に「登録 N 件 / 新着あり N 件 / 新着投稿 計 N 件」を表示
- 「新着のみ表示」スイッチ、および今回の新規 / 総インタラクション / ヒット数 / 関連投稿数 / 最近の活動による並び替えに対応
- メモは常に表示（テーブルでは独立した列）。「この人が主に何を扱っているか」を書くのに、アカウント名より役立ちます
- アカウント名をクリックすると同じドロワーが開き、全関連投稿を確認できます。ドロワー内から登録/解除も可能
- リストは `watchlist.txt` に同期して書き戻されます。**DB が主、ファイルはミラー**なので、ファイルが画面操作で壊れることはありません

> 登録は「選んで追う」だけで、**収集のスイッチではありません**。アカウントはまずキーワードにヒットして DB に入る必要があります。
> まだ DB に入っていないアカウントは `has_posts=false` と 0 の羅列を表示しますが、リストから消えることはありません——
> 消えるとユーザーは登録が効いていないと誤解してしまいます。

### 投稿 ⇄ アカウントの双方向ジャンプ

投稿詳細ドロワーには「@xxx の全関連投稿を見る →」があり、アカウントドロワーで任意の投稿をクリックすると投稿詳細に戻ります。
どちらの方向も**同じドロワーの中身を差し替える**方式で、ルートを積み重ねないため、往復しても履歴スタックの衝突が起きません。

![アカウント詳細ドロワー](docs/author-drawer.png)

アカウントドロワーは、そのアカウントの状況を一度に展開します：関連投稿数、ヒット数、総インタラクション、平均インタラクション、主な領域、
一致したキーワード、そして全関連投稿のリスト。右上の **★ このアカウントを登録** でウォッチリストにワンクリック追加でき、
その後「ウォッチリスト」タブで新着投稿を追えます。

## CSV 書き出し

3 つのビューそれぞれに「CSV 書き出し」ボタンがあります（キーワードレーダー / 競合モニタリング / ウォッチリスト）。

書き出されるのは**今画面に表示されているものそのもの**——絞り込み、検索語、並び順がすべて反映されます。
絞り込んだ後に書き出したら全件が来た、というのは最も批判されやすい不整合です。

Excel 向けの細かい配慮が 2 点あり、どちらが欠けても中国語が文字化けします：

- 先頭に UTF-8 BOM（`\ufeff`）を書く。書かないと Excel が GBK で解釈し、中国語の列がすべて化けます
- 改行コードを `\r\n` に統一。メモ帳も Excel も表全体を 1 行に潰しません

サーバー側には別途 `/api/export` があり（下記参照）、同じ BOM/CRLF 形式を返します。
一括書き出しやスクリプトからの呼び出しに適しており、ブラウザのメモリ上の 3000 件という制限を受けません。

### HTTP API

| メソッド | パス | 説明 |
|---|---|---|
| GET | `/api/status` | 実行状態：進捗、次回収集、チャネル状態、統計、ログ |
| GET | `/api/posts?limit=&only_relevant=` | 投稿一覧 |
| GET | `/api/post/<code>` | 単一投稿の詳細 + エンゲージメント成長曲線 |
| GET | `/api/authors?min_posts=&tier=&sort=&limit=` | **同業ランキング**。`coverage` サンプル厚みを含む |
| GET | `/api/author/<username>` | **あるアカウントの関連投稿一覧** |
| GET | `/api/watchlist` | **ウォッチリスト**。各アカウントのリアルタイム集約と `summary` を含む |
| GET | `/api/export?what=posts\|authors&only_relevant=&limit=` | **CSV 書き出し**（UTF-8 BOM + CRLF、Excel でそのまま開ける） |
| GET | `/api/keywords` | キーワード表 |
| GET | `/api/runs` | 収集履歴 |
| GET | `/api/stream` | SSE リアルタイムプッシュ（状態 / ログ / 進捗） |
| POST | `/api/collect` | 即時収集 |
| POST | `/api/pause` · `/api/resume` | 一時停止 / 再開 |
| POST | `/api/interval` | 収集間隔の変更（`{"minutes": 30}`） |
| POST | `/api/probe` | **チャネル自己診断**（1 リクエストで経路の可否を判定） |
| POST | `/api/keywords` | キーワード追加 |
| POST | `/api/watchlist` | **登録**（`{"username":"@xxx","note":"メモ"}`。アカウント名は正規化されます） |
| POST | `/api/seen` | すべての NEW マークを消去 |
| DELETE | `/api/keywords?keyword=` | キーワード削除 |
| DELETE | `/api/watchlist?username=` | **登録解除** |

`/api/watchlist` のアカウント名は正規化されます：`@Xxx`、`https://www.threads.com/@Xxx/?hl=zh`、
`threads.net/@Xxx/` はすべて小文字の `xxx` に統一されます。正規化しないと `@SomeOne` と `someone`
がリスト内で 2 行になってしまいます。

`/api/posts` と `/api/post/<code>` の各項目には以下のメディアフィールドが付きます：
`media_type`（`19`=テキストのみ / `1`=単一画像 / `8`=カルーセル / `2`=動画）、
`has_image`（その投稿に画像があるか）、`thumb`（サムネイル URL。画像なしの場合は `null`）。
**動画投稿の `media_type` は `2` ですが、サムネイルにはカバーフレームが入ります**——つまり「画像がある」＝「画像投稿」ではないため、
投稿種別の判定は `media_type` で行ってください。

`/api/authors` の `sort` は以下から選択：`hits` / `posts` / `interactions` / `avg_interactions` /
`hit_rate` / `best_score` / `best_likes` / `new_count`。未指定の場合は階層ごとの既定値になります——
主要/継続層はヒット数と産出量、単発層は単一投稿の影響力を見ます。

`/api/export` の `limit` は上限 20000（既定 5000）。`what` は `authors` のみ認識し、それ以外は `posts` として扱われます。

## スコアリング

スコア式は以下です。4 つのエンゲージメント指標はすべて実データから取得します：

```
スコア = (1.0·ln(いいね) + 2.5·ln(返信) + 3.0·ln(リポスト) + 3.0·ln(引用))
         × AI 関連度の重み(1.25 / 1.0)
         × 時間減衰(1/√(1+時間/24))
```

さらに **上昇速度** = インタラクション / 時間 を独立して設けています。バズレーダーで本当に見るべきは「今伸びている」投稿であり、
「累計が多い」古い投稿ではないため、並び替えに独立した選択肢として用意しています。

## 設定

`.env.example` を `.env` にコピーして必要に応じて変更します。すべて既定値があります。
**画面で収集間隔を変更すると `.env` に自動で書き戻される**ので、再起動しても失われません。

> プロキシ（`http_proxy` / `https_proxy`）も `.env` に書きます。設定方法は
> 上記 [まず threads.com に接続できるか確認](#まず-threadscom-に接続できるか確認) を参照してください。

よく変更する項目：

```env
RADAR_INTERVAL_MINUTES=30          # 収集間隔（分）
RADAR_PORT=8650                    # サービスポート
RADAR_SERP_TYPES=base,profile      # 取得バリアント。多いほど網羅的だがレート制限を受けやすい
RADAR_CYCLE_MAX_SECONDS=1800       # 1 サイクルの時間上限（ウォッチドッグ）
RADAR_FAILURE_LIMIT=3              # 空のサイクルが何回続いたら遮断するか
```

> ⚠️ `RADAR_USER_AGENT` は変更しないでください。通常のブラウザ UA にすると空殻ページが返り、収集が完全に機能しなくなります。

## FAQ

**ページは開くが、データが 1 件もない / ずっと収集失敗と表示される。**

まず上部の警告バーに書かれた `reason` を見てください。よくあるのは 2 つ：

- 本機でプロキシが起動していない → `threads.com` へ直結できない（中国国内では既定の状況です）
- プロキシは動いているが出口が Meta のレート制限対象（`proxy_tunnel_502`）→ 取得頻度を下げ、約 20 分で回復するのを待つ

ナビゲーションバーの「**自己診断**」を押すと、サイクル全体の完了を待たずに 1 リクエストだけでチャネルを判定できます。

**「プロキシの障害」と「Threads だけがレート制限」をどう見分けるか？**

`baidu.com` / `api.github.com` と比較してください：この 2 つが通って `threads.com` だけ通らない → 出口がレート制限。
3 つとも通らない → プロキシ自体の問題です。**この切り分けが重要**で、そうしないとコード側で無駄に時間を消耗します。

**ポート 8650 が使われている。**

`.env` の `RADAR_PORT` を変更するか、一時的に環境変数 `set RADAR_PORT=8660` を設定してください。

**関連投稿が少なすぎる。**

Threads の検索は意味ベースの召回なので、関連率は構造的に 4〜5% しかありません。これはプラットフォームの性質でバグではありません。
カバレッジを上げる最も効果的な方法は、フィルタを緩めることではなく**キーワードを増やす**ことと**バリアントを増やす**こと（`RADAR_SERP_TYPES`）です——
緩めるとノイズが増えるだけです。

**同業ランキングでほとんどのアカウントが 1 回しか出てこない。意味がないように見える。**

正常です。初回は 96% の著者が関連投稿を 1 件しか出していません。継続産出ランキングは**十数サイクル**の収集で形になります。
数日動かしてから見直すと全く違って見えます。

**`keywords.txt` を変更したが、既存データの分類が変わらない。**

キーワードは**新規収集**の判定にのみ影響します。既存データを新しいキーワードで再計算するには：

```bash
python refilter.py
```

**データはどこに保存される？ バックアップ / 移行は？**

すべて `data/radar.db` という 1 つの SQLite ファイルに入っています。コピーするだけです（`-wal` も一緒にコピーするとより確実です）。
マシンを移す際は `.env` も持っていってください（変更した間隔などの設定が入っています）。

**X / Instagram / 小紅書も監視できる？**

できません。このプロジェクトは Threads 専用です。他プラットフォームでは取得ロジックが全く異なり、設定変更では対応できません。

**収集は自分の Threads アカウントに影響する？**

**しません**。このプロジェクトはログイン不要で、公開検索ページ + Googlebot UA を使い、あなたのアカウントには一切触れません。
ただし**出口 IP はレート制限を受けます**：実測では 3 バリアント × 19 語を 3 サイクル走らせると 502 になります（約 20 分で回復）。
長時間の稼働ではバリアント ≤2、間隔 ≥30 分を推奨します。

**画面に投稿画像は表示される？**

現在のバージョンでは表示されます。詳細は下記[既知の制限 #10](#既知の制限) を参照してください。これは修正済みの欠落ですが、
**既存の古い投稿のサムネイルは再取得を待つ必要があります**。

## 既知の制限

1. **真のページングカーソルがありません**。「複数バリアント取得」で代替しています（上記参照）。キーワードあたり約 110〜130 件の重複排除済み結果が得られ、関連投稿の産出は 3.1 倍になりました。真のページングには内部 GraphQL の doc_id と実ブラウザセッションが必要で、コストが高く doc_id もローテーションします。
2. **関連率は構造的に低い**：本機で累計 16,710 件を実測し、関連は 730 件で約 **4.4%**
   （2026-09-15 時点）。Threads の検索は意味的マッチングのため、1 語だけ触れた大量の投稿を連れてきます
   （例：`AI art` で検索すると art に言及したありとあらゆる内容が返ります）。キーワードとバリアントの数を増やす方が
   フィルタ調整よりカバレッジ向上に効果的です。
3. **インタラクションが 0 の投稿が多い**：ロングテールが多いためです。画面の「最低インタラクション」スライダーはそのために用意しています。
4. **UA 戦略は回避手段**であり、Meta の公開契約ではありません。いつ厳格化されてもおかしくありません。**取得頻度が高すぎると出口がレート制限を受けます**（実測で 3 バリアントを 3 サイクルで 502、約 20 分で回復）。ログ警告 + チャネル自己診断 + サーキットブレーカーが防衛線です。
5. **`detected_language` は信頼できません**：実測で関連投稿の **81%** が NULL（DB 全体では 45%）。
   言語フィルタに依存できません。言語で絞るなら本文の特徴を自分で見るしかありません。
6. 分類は `keywords.txt` のグループを使います。一致しないものは「未分類」に入ります。
7. 1 サイクルの所要時間は約 2 分/バリアント × キーワード数。キーワード数が大幅に増える場合は収集間隔も合わせて広げないと、サイクルが詰まります。
8. **同業軸は時間の蓄積が必要**。初回の 391 著者のうち関連投稿が ≥2 件なのは 14 件だけで、残り 96% は一度だけの出現です。「継続産出」ランキングを意味のあるものにするには、最低でも十数サイクル必要です。
9. **新規アカウント/新規投稿にはコールドスタートがあります**：`velocity`（インタラクション/時間）は初回収集ではスナップショットが 1 件だけなので、曲線は 2 サイクル目で形になります。
10. **`has_image` が常に 1、画面に画像が出ない —— 修正済みですが、既存のサムネイルは再取得待ちです。**
    これは実際のバグで、本バージョンで修正しました。ただし**古い DB の既存データが勝手に生えてくることはありません**。3 点に分けて説明します：

    - **書き込みロジック（修正済み）**：元の判定は `bool(raw.get("image_versions2"))` でしたが、Threads は
      **すべての**投稿（テキストのみの投稿も含む）に `image_versions2` というキーを返します。
      テキストのみの投稿では値が空殻の `{"candidates": []}` になるため、真偽値が常に真になり、
      実測で 19,963 / 19,963 件すべてが「画像あり」とされていました。現在は
      `bool((raw.get("image_versions2") or {}).get("candidates"))` に変更しています。
      新規取得した 52 件のサンプルで交差検証：`media_type=19`（テキストのみ）33 件は**すべて**画像なし、
      `1`/`8`/`2`（単一画像 / カルーセル / 動画）19 件は**すべて**画像ありで、100% 一致しました。
    - **既存の `has_image`（修正済み）**：起動時にデータ移行を 1 回自動実行します
      （`UPDATE posts SET has_image=0 WHERE media_type=19 AND has_image=1`）。
      冪等で、データは一切削除しません。実測で 13,247 件のテキストのみ投稿を「画像あり」から「画像なし」に戻し、
      19,968 件中 `has_image=1` は 19,966 から 6,719（33.6%）に減少しました。
    - **サムネイル（新規追加。新しい投稿にのみ有効）**：`posts` テーブルに `thumb` 列を追加し、
      リスト / カード / 詳細ドロワーの 3 か所で描画します。CSV 書き出しにもこの列が含まれます。
      ただし**古い行の `thumb` は空です**——当時 URL を保存していないため復元できず、
      これらの投稿が再取得されたときに埋まるのを待つしかありません（書き込みに `COALESCE` を使うため、既存の良いデータを消しません）。
      すぐにすべてのサムネイルを見たい場合は、`data/radar.db` を削除して 1 サイクル回し直してください。
