# Threads バズレーダー

**Threads 上の AI キーワードをリアルタイムで監視し、今まさに伸びている投稿を拾い出す。**

ログイン不要 · OAuth 不要 · 公式 API 不使用 · サードパーティ依存ゼロ · 自分の PC で動かすだけ

## 何を解決するのか

Threads の AI 関連コンテンツは伸びが速く、**ほぼ確実に見逃します**：

- 公式 API の `keyword_search` は**エンゲージメント指標を一切返しません**（いいね・返信・リポスト数が取れない）
- アルゴリズムのフィードを眺めるのはキーワード監視ではなく、ただ餌を与えられているだけ
- バズってから目に入っても、企画のタイミングはもう過ぎている

このツールがやることは単純です：**指定したキーワードを一定間隔で自動収集し、画像があって反応のあるものだけを残し、「今伸びている順」に並べる**。

クローリングフレームワークではなく、常駐させられる単一プロセスです。

## クイックスタート

### 1. threads.com に到達できるか確認

ブラウザで <https://www.threads.com> を開き、正常に表示されれば問題ありません。

**開けない場合**（多くの地域で直結は遮断されています）、まずプロキシが必要です。本プロジェクトは Python 標準ライブラリの `urllib` で取得するため、システムの `http_proxy` / `https_proxy` 環境変数を自動的に読み取ります：

```bat
set http_proxy=http://127.0.0.1:7890
set https_proxy=http://127.0.0.1:7890
```

プロジェクト直下の `.env` に書いてもかまいません（`.env.example` のコメント参照）。

> ⚠ プロキシのポートは、お使いのクライアントの「ミックスポート / HTTP ポート」を指定してください。SOCKS ポートではありません。

### 2. 起動

Windows なら `start.bat` をダブルクリック。またはコマンドラインから：

```bash
python server.py
```

**`pip install` は不要です** —— 使用するのは Python 標準ライブラリのみ。

### 3. 画面を開く

ブラウザで <http://127.0.0.1:8650> にアクセス。

初回起動時に自動で 1 サイクル収集します（3〜5 分程度）。以降は設定した間隔でループします。

## 既定の絞り込みルール

収集される投稿は大量ですが、**読む価値があるものはごくわずか**です。そこで画面には 3 つのゲートが既定で有効です：

| ルール | 既定 | 説明 |
|---|---|---|
| 関連のみ | ✅ オン | 本文がいずれかのキーワードに一致（下記「関連性フィルタ」参照） |
| 画像ありのみ | ✅ オン | **テキストのみの投稿は非表示** —— 視覚的な参考価値がないため |
| 最低インタラクション | **30** | いいね / 返信 / リポストの**いずれか 1 つ**がしきい値を超える |

「最低インタラクション」は**3 つのうち最大値**で判定し、合計ではありません —— 合計にすると「いいね 34 + 返信 33 + リポスト 33」と「いいね 100 + 0 + 0」が同格になりますが、バズなのは後者だけです。引用は判定に含めません（引用は「言及されて議論されている」度合いであり、投稿自身の勢いではないため）。

**3 つのスイッチはすべて画面上にあり、いつでもオフにして全件表示できます。** しきい値は `.env` に固定することもできます：

```ini
RADAR_MIN_INTERACTIONS=30
```

## どうやってデータを取得しているか

### 核心：Googlebot UA + サーバーサイドレンダリング

Threads は通常のブラウザ UA に対して**コンテンツをサーバーサイドレンダリングしません** —— 約 275 KB の空シェルを返し、中身はすべて JS で読み込まれます。

しかし **Googlebot UA** に切り替えると、Meta は完全な SSR ページ（1〜2 MB）を素直に返し、投稿データがインライン JSON として埋め込まれています。

これで次のパイプラインが成立します：

```
Googlebot UA で検索ページをリクエスト
  → SSR HTML を取得
  → <script type="application/json"> から JSON を抽出
  → 投稿オブジェクトを再帰的に特定
  → フィールドを正規化
```

**ログイン不要、OAuth 不要、App Review も不要。**

### ⚠️ コードを触るときに最もハマりやすい点：フィールドの位置

4 つの指標は**同じ階層にありません**：

| フィールド | 位置 |
|---|---|
| `like_count` | 投稿オブジェクトの**トップレベル** |
| `direct_reply_count` | `text_post_app_info` の中（**`reply_count` ではない**点に注意） |
| `repost_count` | `text_post_app_info` の中 |
| `quote_count` | `text_post_app_info` の中 |

したがって「これが投稿オブジェクトか」の判定条件は `code` + `like_count` + `text_post_app_info` の**3 つすべて**である必要があります。最初の 2 つだけで判定すると外側の階層で止まり、残り 3 つがすべて 0 として読まれます。

また `has_image` を `bool(raw.get("image_versions2"))` と書いてはいけません —— Threads は**すべての**投稿（テキストのみを含む）にこのキーを返し、テキストのみの場合は空シェル `{"candidates": []}` です。この真偽値は常に True になります（実測でハマりました：DB 内の約 2 万件がすべて画像ありと誤記録されました）。

## キーワードの書き方

プロジェクト直下の `keywords.txt` を編集するか、画面上で追加・削除します（画面からの変更は同じファイルに書き戻されます）。

```
# 1 行 1 キーワード、[角括弧] はグループ

[モデル]
ChatGPT | GPT | chatgpt
Claude | ClaudeAI | Anthropic Claude

[画像生成]
Midjourney | midjourney
AI art | AI 绘画 | AI画
```

3 つのルール：

- **`|` は同義語** —— 検索には**最初の**表記だけを使いますが、本文がいずれかに一致すれば関連と判定します。精度を落とさずに再現率を補えます（「GPT」としか書かない投稿が非常に多いため）。
- **スペースは AND** —— `AI prompt` は「AI」と「prompt」の両方が必要。連結形も一致します（`#aiprompt`）。
- **`[グループ]`** は画面上の分類用で、自由に変更できます。グループ名は**他の言語に翻訳されません** —— データ値でもあるため、翻訳すると画面上の単語でファイル内を検索できなくなるからです。

## 関連性フィルタ

Threads の検索は「その語を含む投稿」ではなく、**意味的に関連する**結果を返します。実測では「AI prompt」で検索するとインドネシア語・マレー語のエンゲージメント稼ぎ投稿が返り、AI 規制を語る政治家の投稿（1 万いいね超で首位）まで出てきます。AI に多少触れてはいても、企画の役には立ちません。

そこでフィルタ層を用意しています。純粋なキーワード規則で、モデルは呼びません：

| 判定 | 条件 |
|---|---|
| `blocked` | `blocklist.txt` の語に一致 → 即除外 |
| `relevant` | 本文がキーワードに一致（フレーズ全体、または全トークン、または連結形） |
| `offtopic` | それ以外（検索にはヒットしたがキーワードと無関係） |

実装上のポイントが 2 つ：

1. **`ai` のような短い語は部分一致だと誤爆します** —— `said` / `again` / `available`。そのため純 ASCII の語は簡易的な語境界一致（前後に英数字を許さない）を使います。
2. **`tag` フィールドも一致判定に参加します** —— 「AI Threads」コミュニティに属する投稿は、tag から「AI」を供給します。つまり本文が「prompt」だけでもキーワード `AI prompt` に一致します。

**「キーワード一致必須」はこの方式の宿命です**：「ChatGPT Images 2.5 能給我們設計師留一條生路？」のように明らかに AI 関連でも、キーワード表にない語のため offtopic になります。**対処は `keywords.txt` に語を足すことであり、ルールを緩めることではありません** —— 緩めると即座にノイズが溢れます。

### インタラクション 0 の投稿は保存しない

Threads は検索結果の 1 ページを埋めるために、**投稿直後でまったく反応がない**投稿を大量に返します。実測であるサイクルでは 1,421 件を取得して関連は 359 件のみ、残りはほぼすべていいね 0 のキーワード無関係なノイズでした。

そこで収集層にゲートを設けています：**4 指標すべてが 0 の投稿はデータベースに書き込みません**。

これは「永久に捨てる」ではなく**遅延取り込み**です —— 次回取得時にすでに反応があれば、通常どおり保存されます。失うのは「反応ゼロの期間」の伸びの軌跡だけで、投稿そのものを失うわけではありません。

> このルールは「インタラクションが一定値未満なら収集しない」よりはるかに穏やかです：後者はすでに動き始めて伸びている投稿まで遮断してしまいます。

## 取得バリアントと BAN リスク

同じ検索語でも `serp_type` パラメータを変えると**異なるバッチ**が返ります。いわばページ送りです。

実測したバリアント間の重複は **50〜63%** のみ：

| クエリ | base | recent | profile | 3 つの和集合 |
|---|---|---|---|---|
| `q=Claude` | 76 件 | 74 件 | 74 件 | **137 件（+80%）** |
| `q=ChatGPT` | 61 件 | 60 件 | 62 件 | **109 件（+79%）** |

したがってバリアントを増やすのが再現率を上げる最短手段です：

```ini
RADAR_SERP_TYPES=base,profile,recent
```

指定可能な値：`base`（パラメータなし）、`recent`、`top`、`tag`、`profile`、`default`。

### ⚠️ バリアント数が BAN リスクを直接左右します

**本プロジェクトで最も慎重にすべきパラメータです。** 実測値：

| 構成 | リクエスト数 | 結果 |
|---|---|---|
| 3 バリアント × 19 語 | 1 サイクル 57 回（約 114/時） | **3 サイクル連続で threads.com が 502 を返す**、約 20 分で自然回復 |
| 2 バリアント × 19 語 | 1 サイクル 38 回 | 安定 |
| 3 バリアント × 12 語 | 1 サイクル 36 回（約 72/時） | 安定（現在の既定値） |

**推奨**：`キーワード数 × バリアント数 ≤ 40` を守り、間隔は 30 分以上に。制限されたら、**負荷を下げてしばらく待つのが唯一有効な回復手段**です。しつこいリトライは制限を長引かせるだけです。

制限かどうかの切り分け：`threads.com` と無関係なサイト（例：`baidu.com`）を同時にテストします。threads だけ失敗 → 出口 IP が Meta に制限されている。両方失敗 → プロキシが落ちている。

## リアルタイム監視の仕組み

サービス内のバックグラウンドスレッドが、設定間隔で収集をループします。主経路に加えて 4 つの安全装置があります：

- **チャンネル自己診断** —— 現在のプロキシ経路がまだ SSR ページを取得できるかワンクリックで確認し、「スクレイパーの故障」と「出口の遮断」を切り分けます
- **サーキットブレーカー** —— 「1 サイクル完全にゼロ产出」が 3 回続いたら自動一時停止。サイクル全体でゼロならチャンネル障害であり、間隔どおり再試行しても BAN を深めるだけです
- **サイクル全体のウォッチドッグ** —— ノート PC のスリープで収集スレッドが完全に固まります（実測：15.5 時間戻らない）。そこでサイクル単位のタイムアウトを保険として置いています
- **中断実行の後始末** —— プロセスが強制終了されたあと、DB 上で `running` のまま残った実行は自動的に中断として記録されます

## 設定

すべての設定に既定値があり、プロジェクト直下の `.env` に書けば上書きできます（全項目は `.env.example` 参照）。

```ini
RADAR_PORT=8650                        # サービスポート
RADAR_INTERVAL_MINUTES=30              # 収集間隔（分）
RADAR_SERP_TYPES=base,profile,recent   # 取得バリアント：多いほど広いがリスクも上がる
RADAR_MIN_INTERACTIONS=30              # 「最低インタラクション」スライダーの初期値
RADAR_CYCLE_MAX_SECONDS=1800           # 1 サイクルの時間上限（ウォッチドッグ）
RADAR_FAILURE_LIMIT=3                  # ゼロ产出が何サイクル続いたら遮断するか
RADAR_HOST=127.0.0.1                   # バインド先。既定はローカルのみ
```

画面で収集間隔を変更すると**`.env` に書き戻される**ため、再起動しても設定は失われません。

## よくある質問

**Q：起動後ずっと読み込み中 / 0 件しか取れない**
画面の「自己診断」ボタンを押してください。DNS、プロキシトンネル、UA の降格、レート制限のどこで止まっているかを明示します。

**Q：一覧の件数が「DB 内 N 件」よりずっと少ない**
仕様です。DB 内は収集した全量で、一覧は既定で「関連 + 画像あり + インタラクション達成」の分だけを表示します。スイッチをオフにすれば全量が見られます。

**Q：上昇速度の列がすべて 0 なのはなぜ**
速度は**前後 2 回の収集における伸びの差分**から算出します。DB を空にした直後や起動直後は各投稿にスナップショットが 1 つしかなく、2 サイクル以上必要です。

**Q：中国語が文字化けする**
CSV 出力には UTF-8 BOM を付けているので、Excel でそのまま開いても化けません。他の箇所で化ける場合はターミナルのエンコーディングを確認してください（Windows なら `chcp 65001`）。

**Q：サーバーに置いて常時稼働できますか**
可能ですが 2 点注意：① `RADAR_HOST` の既定は `127.0.0.1`（ローカルのみ）で、外部公開には `0.0.0.0` への変更**および自前のリバースプロキシと認証の追加**が必要です —— 本プロジェクトにユーザー管理はありません。② 出口 IP が制限確率を左右し、データセンター IP は通常より制限されやすいです。

## 既知の制限

バグではなく方式上の境界です。無駄な調査を避けるため明記します：

1. **検索の再現率には上限があり、網羅率 100% は不可能。** 1 クエリにつき 1 ページ（約 50〜80 件）しか返らず、コミュニティ（例：「AI Art」）内の投稿直後・反応ゼロの投稿は候補集合に入りません。実測では、投稿の冒頭フレーズそのままで検索しても **0 件** —— Threads の検索は**全文インデックスではなく**、アルゴリズムによる候補集合です。
2. **コミュニティページは取得できません。** ブラウザで見える「トピックコミュニティページ」（人気／最新タブ付き）は JS レンダリングで、ヘッドレス SSR では退化した結果しか得られません（実測：無関係な投稿ばかり）。対応には JS レンダリング + ログインセッションが必要で、本プロジェクトの「依存ゼロ・ログイン不要」と真っ向から衝突します。
3. **投稿直後のコンテンツはノイズだらけ。** 実測であるサイクルの新規取り込み投稿の関連率は **1.5%** のみ（既存投稿は 34〜59%）。「リアルタイム」と「関連性」は本質的にトレードオフで、「反応ゼロは保存しない」で大半を除去しています。
4. **インタラクションが大量に 0 なのは正常。** ロングテールが大多数で、そのために「最低インタラクション」スライダーがあります。
5. **Threads のページ構造に依存。** Meta が SSR データの構成を変えれば、解析ロジックも追従が必要です。`collector.py` 冒頭のコメントにフィールド位置を明記しているので、修正は難しくありません。
6. **単一マシン・単一プロセス・認証なし。** 自分の PC に常駐させる個人ツールであり、マルチユーザーサービスではありません。

## ファイル構成

```
threads-ai-radar/
├── server.py          HTTP サービス + JSON API + 静的ファイル
├── monitor.py         バックグラウンド制御：定期収集、自己診断、遮断、ウォッチドッグ
├── pipeline.py        1 サイクルの編成：収集 → 関連性判定 → スコア → 保存
├── collector.py       収集層：Googlebot UA で SSR ページを取得しインライン JSON を解析
├── relevance.py       関連性判定：純キーワード規則（blocked / relevant / offtopic）
├── scorer.py          バズスコアと上昇速度
├── store.py           SQLite 保存：スキーマ、マイグレーション、クエリ、アカウント集計
├── config.py          設定読み込み（.env と環境変数）
├── selftest.py        自己診断：フィルタとランキングを実行し、除外サンプルを表示
├── refilter.py        キーワード変更後、既存データを再フィルタ（再収集不要）
├── start.bat          Windows 用ワンクリック起動
├── requirements.txt   空 —— 本プロジェクトはサードパーティ依存ゼロ
├── keywords.txt       監視キーワード（画面から編集可、本ファイルに書き戻し）
├── blocklist.txt      ブロック語（一致したら即除外）
├── watchlist.txt      ウォッチするアカウント
├── .env.example       設定例
├── data/
│   └── radar.db       SQLite データベース（サンプルデータ同梱、すぐ画面を確認できます）
├── docs/              本 README で使うスクリーンショット
└── web/
    ├── index.html     単一ファイルのフロントエンド（フレームワークなし、ビルドなし）
    └── i18n.js        5 言語の辞書とランタイム（簡中 / 英 / 繁中 / 日 / 韓）
```

**UI は 5 言語対応**：简体中文、English、繁體中文、日本語、한국어。右上で切り替え、選択は localStorage に保存されます。UI の文言はすべて翻訳しますが、**投稿本文・アカウント名・グループ名は翻訳しません** —— それらはデータであり、インターフェースではないからです。
