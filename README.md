# Threads 爆款雷达 · 实时关键词监控

监控 Threads 上与你关注的关键词相关的公开帖子，实时汇总成一张榜单。

**零第三方依赖，只用 Python 标准库**——装好 Python 就能直接跑，不用 `pip install`。

![License](https://img.shields.io/badge/License-MIT-blue.svg)
![Python](https://img.shields.io/badge/Python-3.10%2B-3776AB.svg)
![Dependencies](https://img.shields.io/badge/dependencies-none-brightgreen.svg)
![Platform](https://img.shields.io/badge/platform-Windows%20%7C%20macOS%20%7C%20Linux-lightgrey.svg)

三个视图回答三个不同的问题：

| 视图 | 回答的问题 |
|---|---|
| **关键词雷达** | 哪条**帖子**正在火 |
| **同行监控** | 谁在**持续产出**爆款（按账号聚合 + 持续度分层） |
| **关注名单** | **我盯的人**里，谁刚发了新东西 |

每个视图都能把当前筛选结果导出成 CSV（Excel 直开不乱码）。

### 特性一览

- **真·实时**：常驻进程按间隔自动采集，页面走 SSE 推送，采集完立即刷新，不用手动点
- **四个互动指标齐全**：点赞 / 回复 / 转发 / 引用，一个都不少（官方 API 拿不到这些）
- **带缩略图**：列表 / 卡片 / 详情三处都能看图，并标出这条是纯文字 / 单图 / 多图 / 视频 —— 判断爆款不用逐条点开
- **上涨速度单列**：`互动量 / 小时`，看的是「正在涨」而不是「历史总量高」
- **互动增长曲线**：每次采集写一条快照，详情里能看到一条帖子的增长轨迹
- **通道健康检查 + 熔断**：失败原因分类到具体理由，连续零产出自动停，不硬敲被封的出口
- **零依赖**：只用 `urllib` / `sqlite3` / `http.server` / `threading`，长期挂机不易因环境问题中断
- **五语界面**：简体中文 / English / 繁體中文 / 日本語 / 한국어，导航栏右上角一键切换，选择记在浏览器里；数据侧的值（分组名、关键词、账号名、帖子正文）绝不翻译，保证界面上的词能直接拿去配置文件里搜
- **三档响应式**：桌面 / 平板 / 移动，实测 54 种宽度×视图组合无横向溢出

## 快速开始

需要 **Python 3.10 以上**，不需要 `pip install`（零第三方依赖）。

```
双击 start.bat
```

或者：

```bash
python server.py
```

然后浏览器打开 **http://127.0.0.1:8650**

启动时会立刻跑第一轮采集，之后按设定间隔自动循环。

### 先确认能访问 threads.com

这是**唯一一个容易卡住的地方**。程序用 Python 标准库 `urllib` 抓取，
`urllib` 会自动读取系统的 `http_proxy` / `https_proxy` 环境变量，
所以直连不通时按下面任一种方式配上代理即可。

**方式一：填进 `.env`**（推荐，跟着项目走）

```bash
cp .env.example .env          # Windows: copy .env.example .env
```

然后编辑 `.env`，取消注释并改成你自己的端口：

```env
http_proxy=http://127.0.0.1:7890
https_proxy=http://127.0.0.1:7890
```

**方式二：设成系统环境变量**（Windows 命令行临时生效）

```bat
set http_proxy=http://127.0.0.1:7890
set https_proxy=http://127.0.0.1:7890
```

> 端口去哪找：Clash / v2rayN 等客户端里的「HTTP 端口」或「混合端口」。
> **不要写 `socks5://`** —— `urllib` 不支持 socks 代理，必须用 HTTP 端口。

配完可以点界面右上角的 **通道自检**（`POST /api/probe`）验证，
或直接用命令行确认：

```bash
python -c "from collector import probe_channel; print(probe_channel())"
```

> ⚠️ 代理必须开着才能采集。关掉代理后通道会报 502（`proxy_tunnel_502`）。
> 排查时先拿 `baidu.com` / `api.github.com` 对比：这两个通、只有 `threads.com`
> 不通 → 出口被 Meta 风控（降低频率，约 20 分钟自愈）；三个都不通 → 代理本身挂了。
> 通道状态和失败原因都会显示在界面顶部的告警条里。

## 部署 / 给别人用

**本项目定位是「单机自用的实时监控台」，不是公网服务**，默认只监听 `127.0.0.1`。
给别人用最简单的办法就是让对方 clone 下来自己跑。

```
git clone https://github.com/BaYue-SYJ/threads-ai-radar.git
cd threads-ai-radar
# 配好代理（见上节）
start.bat            # 或 python server.py
```

三条须知：

1. **不需要装任何依赖**，装好 Python 就能跑。数据库 `data/radar.db` 首次启动自动创建。
2. **每台机器各自采各自的数据**。本程序不带账号体系，也不做数据同步。
   想两个人看同一份榜单，就都连到同一台机器（见下条）。
3. **不要在公网上裸奔**。HTTP 服务没有任何鉴权，任何能访问到端口的人
   都能改你的关键词和关注名单。真要局域网共享，请只绑内网地址：

   ```env
   RADAR_HOST=0.0.0.0        # 或在 .env 里绑具体内网 IP，如 192.168.1.10
   ```

   然后靠防火墙限制来源 IP。**不要**做端口转发到公网。

## 它是怎么抓到数据的

这是整个项目最关键的一点，先说清楚。

**官方 Threads API 这条路走不通：** `keyword_search` 需要过 Meta App Review；未过审前只返回你自己发的帖子；而且响应里**根本不含**点赞 / 回复 / 转发 / 引用这四个数字。一个拿不到互动数据的「爆款雷达」等于不存在。

**实际采用的是：Googlebot UA + 服务端渲染。**

| 请求方式 | 返回内容 |
|---|---|
| 普通浏览器 UA | ~275KB 的 SPA 空壳，**没有任何帖子数据** |
| `Googlebot` UA | **1.0~1.9MB 完整 SSR 页面**，帖子数据以内嵌 JSON 直接给出 |

免登录、无需 OAuth、无需 App Review、零成本，四个互动指标全部可取。

### 字段位置（改代码时最容易踩的坑）

四个指标**不在同一层**：

| 字段 | 位置 |
|---|---|
| `like_count` | 帖子对象**顶层** |
| `direct_reply_count` | `text_post_app_info` 内，**注意不叫 `reply_count`** |
| `repost_count` | `text_post_app_info` 内 |
| `quote_count` | `text_post_app_info` 内 |

判定一个对象是不是帖子，条件必须同时包含 `code` + `like_count` + `text_post_app_info`。
只写前两个会**停在外层不再下钻**，后三个字段会全部读成 0——这个坑我在开发时真踩过一次。

## 关键词怎么写

编辑 `keywords.txt`，或者直接在界面顶部的「监控关键词」面板里增删。

```
[模型]                    ← 方括号是分组，会直接用作界面上的分类
ChatGPT | GPT | chatgpt   ← 竖线分隔同义词
AI prompt                 ← 空格 = AND
```

- **空格 = AND**：`AI prompt` 要求正文同时出现 AI 和 prompt
- **竖线 = OR**：`ChatGPT | GPT` 命中任意一个即算相关。
  **只用第一个写法去搜索**，后面的只用于判定。很多帖只说 `GPT` 不写全称，加同义词才不会漏。
- 自动兼容话题标签连写：`#aiprompt` 也能命中 `AI prompt`
- 对 `ai` 这类短词用近似词边界匹配，不会误伤 `said` / `available`

## 相关性过滤

Threads 的搜索是**语义召回**，不是「正文含该词」召回。实测搜 `AI prompt` 会返回印尼语蹭流量帖、甚至政治人物谈 AI 监管的帖子（11,168 赞冲上榜首）。

所以每轮采集后都会给帖子打一个判定：

| 判定 | 含义 |
|---|---|
| **相关** | 正文命中关键词短语，或全部有效词，或同义词 |
| **无关** | 被搜索召回，但正文与关键词无关 |
| **屏蔽** | 命中 `blocklist.txt` 的噪音词 |

界面上的「**仅看相关**」开关控制是否显示后两类，默认开启。

**相关率天然偏低，实测约 4%**——这是 Threads 搜索的固有特性，不是 bug。
本机累计 16,710 条召回里筛出 730 条相关（**4.4%**，2026-09-15 快照）。
极端例子：搜 `Nano Banana` 召回 64 条，其中含 "banana" 的是 **0 条**——
全是印尼语「nano KOL」营销帖，过滤器正确地把它们全挡掉了。

> 相关率低不等于没用：过滤掉的是语义噪音，留下的是真命中。
> 想提高覆盖面，加关键词和变体比调过滤器更有效。

改完关键词或屏蔽词后想重新判定已有数据，不用重抓：

```bash
python refilter.py
```

## 抓取变体（相当于翻页）

Threads 搜索页的 `serp_type` 参数会返回**不同批次**的结果。多取几个变体再合并去重，
效果相当于翻页——这比走内部 GraphQL 拿游标更可靠（实测 GraphQL 通道需要真实浏览器
会话的 cookie + csrf，直接 POST 只会返回 HTML 外壳；而且 doc_id 会轮换）。

**⚠️ 选变体要看「相关帖产出」，不能看「原始条数」——两者差异极大。**

实测各变体新增的**相关帖**数（以 base 为基准）：

| 关键词 | base | recent | top | tag | **profile** | **default** |
|---|---|---|---|---|---|---|
| ChatGPT | 15 | +0 | +0 | +0 | **+17** | +9 |
| Nano Banana | 3 | +0 | +2 | +1 | **+13** | +7 |
| AI prompt | 21 | +6 | +0 | +1 | +0 | **+10** |

`recent` 原始条数新增很多，但**几乎全是语义噪音**；真正的价值在 `profile` 和 `default`。
我最初按原始条数选了 `base,recent,top`，实际挑中的是两个最弱的变体——按相关帖产出重选后才拿到真实收益。

三变体实测效果：

| | 单变体 | 三变体 | 提升 |
|---|---|---|---|
| 库内总数 | 980 | **3,865** | 3.9× |
| **相关帖子** | 136 | **415** | **3.1×** |
| 覆盖账号 | 941 | 3,562 | 3.8× |
| 每轮耗时 | ~2 分钟 | ~7 分钟 | 3.5× |

### ⚠️ 变体数与封禁风险直接相关（实测踩过）

三变体 × 19 关键词 = **57 请求/轮**，跑满三轮后 `threads.com` 开始对本机出口返回：

```
urllib.error.URLError: Tunnel connection failed: 502 Bad Gateway
```

同时 `baidu.com`、`api.github.com` 仍是 200 —— 说明**不是代理挂了，也不是 Threads 下线**，而是出口 IP 被 Meta 风控。约 20 分钟后自行恢复。

结论：**长期挂机用 2 个变体以内**（默认 `base,profile`），间隔拉到 30 分钟以上。被限后唯一有效的恢复手段是降低压力 + 停一段时间，硬重试只会延长封锁。

> 排查此类问题必须先分通道验证：拿 `baidu.com` / `api.github.com` 对比，才能把「代理整体故障」和「单一目标被风控」区分开。

## 实时监控怎么工作

`server.py` 启动时会在进程内拉起一个后台调度线程：

- 按固定间隔（默认 15 分钟）循环采集全部关键词
- 关键词之间插入 1.8~4.2 秒**随机抖动**，避免固定节奏触发风控
- 页面通过 **SSE**（`/api/stream`）接收推送，每 2 秒同步一次状态，采集完成立即刷新榜单
- 每次采集都会往 `snapshots` 表写一条互动数快照，详情抽屉里能看到增速曲线

界面上能看到：

- 导航栏实时状态点：**监控中 / 采集中 / 已暂停 / 通道异常**
- 下次采集**倒计时**
- 采集进度条 `7/19 · Midjourney`
- 滚动采集日志（含异常告警）
- 新入库帖子带 **NEW** 角标

### 响应式

三个视图都适配桌面 / 平板 / 移动三档，实测 **18 个宽度（390~1680px）× 3 个视图 = 54 种组合均无横向溢出**：

<p align="center">
  <img src="docs/mobile.png" width="380" alt="手机端关键词雷达">
</p>

| 断点 | 导航栏 | 同行表格 | 关注名单表格 |
|---|---|---|---|
| ≥1181px | 单行 | 全部 11 列 | 全部列 |
| 1081~1180px | 收紧间距 | 隐藏爆款率 / 均互动 / 最高分（爆款率可由帖数算出） | 隐藏主攻方向（把宽度让给备注） |
| ≤1080px | 操作区换到第二行 | 同上 | 同上 |
| ≤860px | 同上 | 默认切到**卡片视图**；若手动切表格，容器内可横向滑动（不静默裁列） | 同上；表单改为整行堆叠 |

> 踩坑记录：加第三个标签（关注名单）之后，导航栏的最小内容宽度涨到 **1078px**。
> 原来只在 860px 断点做换行，结果 **1024px 时右侧控件被挤出屏幕 54px**——
> 桌面和手机都正常，只有中间这一段坏，很容易漏掉。
> 现在的做法是单行塞不下就整体下移，而不是继续压间距：压到后面按钮会挤成一团。
>
> 顺带一个坑：**`getBoundingClientRect().right > clientWidth` 的溢出检测会把关闭状态的抽屉全算成溢出**
> ——它是靠 `translateX(101%)` 挪到屏幕外的。检测脚本必须排除抽屉，否则每个宽度都误报。
> 更可靠的判据是 `documentElement.scrollWidth > clientWidth`。

### 健康检查与通道自检

每次抓取都会校验「响应体积 ≥ 400KB 且解析出 ≥ 5 条帖子」，不达标记为异常。

但光有体积检查不够——**「抓到了但页面没数据」和「链路根本不通」是两回事**，前者重启抓取器就行，
后者硬重试只会加深风控。所以失败会被归到具体原因：

| reason | 含义 | 该怎么办 |
|---|---|---|
| `proxy_tunnel_502` | 代理隧道 502，出口被拒 | 降低频率 + 停一段时间 |
| `rate_limited` | HTTP 429 被限流 | 减少变体数、拉长间隔 |
| `connect_timeout` | 直连被阻断 | 走可用代理 |
| `tls_reset` | TLS 被中间设备重置 | 换链路 |
| `gateway` | 上游 5xx | 一般可自愈 |
| `empty_shell` | 拿到页面但无 SSR | UA 被降级，检查是否改过 `RADAR_USER_AGENT` |

点导航栏的「**自检**」或直接调 `/api/probe`，会发**一个**请求快速判定通道状态，不用等整轮跑完。

![通道异常告警条](docs/channel-alert.png)

上图为出口被风控时的真实界面：顶部红条给出**具体原因**（`proxy_tunnel_502`）和
**可执行建议**（停一段时间再试、或降低变体数），而不是只在日志里留一行「页面异常」。
导航栏状态点也会同步变成「通道异常」。

### 熔断

一旦出现**整轮零产出**（19 个关键词一条都没抓到），说明是通道级故障而非个别关键词没数据。
连续 **3 轮**如此会**自动暂停监控**并在日志里说明原因——避免按间隔持续敲打一个已被封的出口。

界面上会顶出一条红色告警条，写明原因和建议，而不是只在日志里留一行「页面异常」。

### 整轮看门狗

单轮采集有**硬性时间上限**（`RADAR_CYCLE_MAX_SECONDS`，默认 1800 秒 = 30 分钟）。
到点就中止本轮，日志写明在第几个关键词处停下、为什么。

为什么需要：**笔记本休眠会把采集线程整个冻住**。实测跑完第 7 个关键词后机器进入休眠，
线程停在原地 **15.5 小时**没有返回（跨休眠时单个请求的 socket 超时未必生效），
期间下一轮采集一直被阻塞。看门狗在每个关键词开始前检查是否超时，恢复后立刻收尾退出，
下一轮才能正常开始。

提前中止时 `keywords_done` 会按**实际跑完的数量**如实记录（如 `9/19`），
不会谎报成「本轮全部完成」。

### 中断残留记录自动收尾

进程被强杀（或看门狗中止）时，采集记录会停在 `running`。启动时会自动扫一遍，
把这类记录标成 `error / 进程中断，本轮未完成`——否则界面上会一直显示「采集中」，
让人觉得工具卡死了。

## 同行 / 竞品监控

关键词榜回答的是「**哪条帖子火了**」；同行榜回答的是「**谁在持续产出爆款**」。
后者要按作者聚合，而且是这个项目真正的差异化点——竞品监控看的是人和方法论，不是单条帖子。

界面顶部第二个标签「**同行监控**」，按作者聚合相关帖：

- **分层**：按持续度自动打标，这才是筛选监控目标的依据

  | 分层 | 条件 | 含义 |
  |---|---|---|
  | 核心监控 | 帖 ≥ 3 且 爆款 ≥ 2 | 方法论稳定，值得长期盯 |
  | 持续产出 | 帖 ≥ 2 | 有稳定输出 |
  | 单帖爆款 | 帖 = 1 且 爆款 ≥ 1 | 可能是运气 |
  | 偶发出现 | 其余 | 一次性出现 |

  （爆款 = 单条帖子互动量 ≥ 500，阈值见 `store.HIT_THRESHOLD`）

- **每行给出**：相关帖数、爆款数、爆款率、总互动、单帖均互动、最高评分、主攻方向、最近活跃
- **点任意账号**打开抽屉：分层、发帖节奏（约 N 帖/周）、主攻方向、命中关键词，以及该账号全部相关帖
- **排序**：爆款数 / 相关帖数 / 总互动 / 单帖均互动 / 爆款率 / 最高评分 / 最高点赞 / 本轮新增

### 为什么一定要做「持续度」过滤

数据量小时，绝大多数账号只出现过一次。实测首轮 391 个作者里：

```
帖数 ≥ 1：391        帖数 ≥ 2：14        帖数 ≥ 3：5
分层分布：核心监控 1 / 持续产出 13 / 单帖爆款 50 / 偶发出现 327
```

**96% 的账号是「一次性出现」**。如果直接按爆款数排序，榜单会被单帖作者占满，完全看不出谁值得长期盯。
所以默认提供「只看持续产出（≥2 帖）」开关，且各分层有各自的默认排序字段。

界面顶部会显示样本厚度，说明「持续产出」人数少是因为采集轮次还不够，而不是功能坏了。
**多跑几轮，这个榜才真正有信息量**——这也是账号维度必须靠时间累积的原因。

## 关注名单

同行榜是「全站扫出来的排名」，关注名单是「**我自己圈出来要盯的人**」。这两件事需要不同的界面：
前者要全、要能排序找规律；后者要短、要一眼看出谁刚发了新东西。

第三个标签「**关注名单**」，三个入口都能加人：

- 同行监控页每行/每张卡左边的 **☆** 一键关注（表格和卡片视图都有）
- 关注名单页顶部的输入框，账号可直接粘贴 `@xxx`、`xxx/` 或整条主页/帖子链接
- 直接编辑 `watchlist.txt`，格式 `账号 | 备注`，重启后自动读入

关注之后：

- **有新帖的排最前**，带 `+N` 蓝色徽章；顶部给出「关注 N 个 / 有 N 个有新帖 / 共 N 条新帖」
- 支持「只看有新帖」开关，以及按本轮新增 / 总互动 / 爆款数 / 相关帖数 / 最近活跃排序
- 备注会一直显示（表格里独立一列），用来记「这人主攻什么」比记账号名有用
- 点账号名打开同一个抽屉，可看全部相关帖；抽屉里还能直接关注/取关
- 名单会同步写回 `watchlist.txt`，**库是主、文件是镜像**，所以文件不会被界面改乱

> 关注只做「挑出来盯住」，**不是采集开关**。账号得先被关键词命中入库才有数据；
> 还没进过库的账号会显示 `has_posts=false` 和一堆 0，而不是从名单里消失——
> 否则用户会以为关注没生效。

### 帖子 ⇄ 账号 双向跳转

帖子详情抽屉里有「看 @xxx 的全部相关帖 →」，账号抽屉里点任意一条帖子回到帖子详情。
两个方向都在**同一个抽屉里换内容**，不叠加路由，所以来回跳不会出现历史栈冲突。

![账号详情抽屉](docs/author-drawer.png)

账号抽屉把该账号的情况一次铺开：相关帖数、爆款数、总互动、均互动、主攻方向、
命中关键词，以及全部相关帖列表。右上角的 **★ 关注该账号** 可一键加进关注名单，
随后就能在「关注名单」标签里专门盯它有没有发新东西。

## CSV 导出

三个视图各有一个「导出 CSV」按钮（关键词雷达 / 同行监控 / 关注名单）。

导出的**就是当前屏幕上这一份**——筛选、搜索词、排序全部带上。
筛完一片再导出却拿到全量，是最容易被骂的那种不一致。

两个细节是为 Excel 准备的，缺一个中文就乱码：

- 开头写 UTF-8 BOM（`\ufeff`）。不写的话 Excel 按 GBK 解码，中文列全变乱码
- 统一 `\r\n` 行尾，记事本和 Excel 都不会把整表挤成一行

服务端另有 `/api/export`（见下），返回同样的 BOM/CRLF 格式，
适合批量导出和脚本调用——不受浏览器内存里那 3000 条的限制。

### HTTP 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/status` | 运行状态：进度、下次采集、通道状态、统计、日志 |
| GET | `/api/posts?limit=&only_relevant=` | 帖子列表 |
| GET | `/api/post/<code>` | 单帖详情 + 互动增长曲线 |
| GET | `/api/authors?min_posts=&tier=&sort=&limit=` | **同行榜**，含 `coverage` 样本厚度 |
| GET | `/api/author/<username>` | **某账号的相关帖列表** |
| GET | `/api/watchlist` | **关注名单**，含每个账号的实时聚合与 `summary` |
| GET | `/api/export?what=posts\|authors&only_relevant=&limit=` | **CSV 导出**（UTF-8 BOM + CRLF，Excel 直开） |
| GET | `/api/keywords` | 关键词表 |
| GET | `/api/runs` | 采集历史 |
| GET | `/api/stream` | SSE 实时推送（状态 / 日志 / 进度） |
| POST | `/api/collect` | 立即采集 |
| POST | `/api/pause` · `/api/resume` | 暂停 / 恢复 |
| POST | `/api/interval` | 改采集间隔（`{"minutes": 30}`） |
| POST | `/api/probe` | **通道自检**（发 1 个请求判定链路是否可用） |
| POST | `/api/keywords` | 新增关键词 |
| POST | `/api/watchlist` | **加关注**（`{"username":"@xxx","note":"备注"}`，账号名会归一化） |
| POST | `/api/seen` | 清掉所有 NEW 标记 |
| DELETE | `/api/keywords?keyword=` | 删除关键词 |
| DELETE | `/api/watchlist?username=` | **取消关注** |

`/api/watchlist` 的账号名做了归一化：`@Xxx`、`https://www.threads.com/@Xxx/?hl=zh`、
`threads.net/@Xxx/` 都会统一成小写 `xxx`；不归一化的话 `@SomeOne` 和 `someone`
会在名单里变成两行。

`/api/posts` 与 `/api/post/<code>` 每条都带这几个媒体字段：
`media_type`（`19`=纯文字 / `1`=单图 / `8`=多图 / `2`=视频）、
`has_image`（该帖是否有图）、`thumb`（缩略图 URL，无图时为 `null`）。
**视频帖的 `media_type` 是 `2`，但缩略图里放的是封面帧**——所以「有图」不等于「是图片帖」，
判断帖子类型要看 `media_type`。

`/api/authors` 的 `sort` 可选：`hits` / `posts` / `interactions` / `avg_interactions` /
`hit_rate` / `best_score` / `best_likes` / `new_count`。不传时按分层给默认值——
核心/持续层看爆款数与产出，单帖层看单条影响力。

`/api/export` 的 `limit` 上限 20000（默认 5000），`what` 只认 `authors`，其余按 `posts` 处理。

## 评分

评分公式如下，四个互动指标都取自真实数据：

```
评分 = (1.0·ln(赞) + 2.5·ln(回) + 3.0·ln(转) + 3.0·ln(引))
       × AI 相关度加权(1.25 / 1.0)
       × 时间衰减(1/√(1+小时/24))
```

另外单列一项 **上涨速度** = 互动量 / 小时。爆款雷达真正该看的是「正在涨」的帖子，
而不是「历史总量高」的老帖，所以排序里把它单独放了一个选项。

## 配置

复制 `.env.example` 为 `.env` 后按需修改，全部有默认值。
**界面里改采集间隔会自动写回 `.env`**，重启不会丢。

> 代理（`http_proxy` / `https_proxy`）也写在 `.env` 里，配置方法见
> 上文 [先确认能访问 threads.com](#先确认能访问-threadscom)。

最常改的：

```env
RADAR_INTERVAL_MINUTES=30          # 采集间隔（分钟）
RADAR_PORT=8650                    # 服务端口
RADAR_SERP_TYPES=base,profile      # 抓取变体，越多越全但越容易被风控
RADAR_CYCLE_MAX_SECONDS=1800       # 单轮时间上限（看门狗）
RADAR_FAILURE_LIMIT=3              # 连续几轮零产出后熔断
```

> ⚠️ 不要改 `RADAR_USER_AGENT`。换成普通浏览器 UA 会拿到空壳页面，整个采集直接失效。

## 常见问题

**页面能打开，但一条数据都没有 / 一直显示采集失败。**

先看顶部告警条写的 `reason`，最常见两种：

- 本机没开代理 → 直连 `threads.com` 不通（这在国内是默认情况）
- 代理开着但出口被 Meta 风控（`proxy_tunnel_502`）→ 降低抓取频率，等约 20 分钟自愈

点导航栏的「**自检**」可以只发 1 个请求判定通道，不用等一整轮跑完。

**怎么区分「代理挂了」和「只有 Threads 被风控」？**

拿 `baidu.com` / `api.github.com` 对比：这两个通、只有 `threads.com` 不通 → 出口被风控；
三个都不通 → 代理本身有问题。**这个区分很关键**，否则容易在代码上白耗时间。

**端口 8650 被占用了。**

改 `.env` 里的 `RADAR_PORT`，或临时设环境变量 `set RADAR_PORT=8660`。

**相关帖太少了。**

Threads 搜索是语义召回，相关率天然只有 4~5%，这是平台特性不是 bug。
提升覆盖面最有效的办法是**加关键词**和**多变体**（`RADAR_SERP_TYPES`），而不是放宽过滤器——
放宽只会让噪音变多。

**同行榜里大部分账号只出现过一次，看着没意义。**

正常。首轮 96% 的作者都只发过 1 条相关帖。持续产出榜需要**十几轮**采集才成形，
挂几天再回来看会完全不一样。

**改了 `keywords.txt`，已有数据的分类没跟着变。**

关键词只影响**新采集**的判定。让已有数据按新关键词重算：

```bash
python refilter.py
```

**数据存哪？怎么备份 / 迁移？**

全在 `data/radar.db` 一个 SQLite 文件里，拷走即可（连 `-wal` 一起拷更稳）。
换机器时把 `.env` 也带上（里面是你改过的间隔等设置）。

**能监控 X / Instagram / 小红书吗？**

不能，本项目只做 Threads。换平台的抓取逻辑完全不同，不是改配置能解决的。

**采集会不会影响我的 Threads 账号？**

**不会**。本项目不需要登录，用的是公开搜索页 + Googlebot UA，全程不碰你的账号。
但**出口 IP 会被风控**：实测 3 变体 × 19 词连跑三轮就会 502（约 20 分钟自愈）。
长期挂机建议 ≤2 变体 + 间隔 ≥30 分钟。

**界面会显示帖子图片吗？**

当前版本不会，原因见下方[已知限制 #10](#已知限制)。这是已知缺口，计划在后续版本修。

## 已知限制

1. **没有真正的分页游标**。已用「多变体抓取」替代（见上节），每个关键词约 110~130 条去重结果，相关帖产出提升 3.1 倍。要走真分页得拿到内部 GraphQL 的 doc_id 并提供真实浏览器会话，成本高且 doc_id 会轮换。
2. **相关率天然偏低**：本机累计实测 16,710 条帖子里相关帖 730 条，约 **4.4%**
   （2026-09-15 快照）。原因是 Threads 搜索属于语义匹配，会带回大量只沾一个词的帖子
   （例：搜 `AI art` 会返回任何提到 art 的内容）。增加关键词和变体数量
   比调过滤器更能提升覆盖面。
3. **互动数大量为 0**：长尾帖居多，界面「最低互动」滑块就是为此准备的。
4. **UA 策略属于绕过手段**，不是 Meta 的公开契约，随时可能收紧；**抓取频率过高会触发出口风控**（实测 3 变体跑满 3 轮即被 502，约 20 分钟自愈）。日志告警 + 通道自检 + 熔断就是防线。
5. **`detected_language` 不可靠**：实测相关帖里 **81%** 为 NULL（全库 45%），
   不能依赖它做语言过滤。要按语言筛只能自己看正文特征。
6. 分类采用 `keywords.txt` 里的分组，未命中的归入「未分组」。
7. 每轮耗时约 2 分钟/变体 × 关键词数。若关键词数量大增，需同步调大采集间隔，否则轮次会挤在一起。
8. **同行维度需要时间积累**。首轮 391 个作者里只有 14 个发过 ≥2 条相关帖，其余 96% 是一次性出现。想让「持续产出」榜有意义，至少得跑十几轮。
9. **新账号/新帖有冷启动**：`velocity`（互动/小时）在首次采集时只有一条快照，曲线要等第二轮才成形。
10. **`has_image` 恒为 1、界面不显示图片 —— 已修复，但存量缩略图要等回补。**
    这是个真实 bug，已在本版本修掉；但**老库里的旧数据不可能凭空变出来**，分三件事说：

    - **写入逻辑（已修）**：原判定是 `bool(raw.get("image_versions2"))`，但 Threads
      给**每一条**帖子（含纯文字帖）都返回 `image_versions2` 这个 key，
      纯文字帖的值是空壳 `{"candidates": []}`——布尔值因此恒为真，
      实测 19,963 / 19,963 条全被标成「有图」。现改为
      `bool((raw.get("image_versions2") or {}).get("candidates"))`。
      新抓 52 条样本交叉验证：`media_type=19`（纯文字）33 条**全部**无图，
      `1`/`8`/`2`（单图 / 多图 / 视频）19 条**全部**有图，100% 吻合。
    - **存量 `has_image`（已修）**：启动时自动跑一次数据迁移
      （`UPDATE posts SET has_image=0 WHERE media_type=19 AND has_image=1`），
      幂等、不删任何数据。实测把 13,247 条纯文字帖从「有图」改回「无图」，
      19,968 条里 `has_image=1` 从 19,966 降到 6,719（33.6%）。
    - **缩略图（新增，只对新帖生效）**：`posts` 表新增 `thumb` 列，
      列表 / 卡片 / 详情抽屉三处都会渲染，CSV 导出也带上了这一列。
      但**老行的 `thumb` 是空的**——当年压根没存过 URL，无从恢复，
      只能等这些帖被再次采集到时回填（写入用 `COALESCE`，不会把已有的好数据擦掉）。
      想立刻看到全部缩略图，删掉 `data/radar.db` 重跑一轮即可。
