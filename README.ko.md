# Threads 버즈 레이더 · 실시간 키워드 모니터링

Threads에서 관심 키워드와 관련된 공개 게시물을 모니터링하여 실시간 순위표로 정리합니다.

**서드파티 의존성 제로, Python 표준 라이브러리만 사용**——Python만 설치되어 있으면 바로 실행됩니다. `pip install`이 필요 없습니다.

![License](https://img.shields.io/badge/License-MIT-blue.svg)
![Python](https://img.shields.io/badge/Python-3.10%2B-3776AB.svg)
![Dependencies](https://img.shields.io/badge/dependencies-none-brightgreen.svg)
![Platform](https://img.shields.io/badge/platform-Windows%20%7C%20macOS%20%7C%20Linux-lightgrey.svg)

세 가지 뷰가 세 가지 질문에 답합니다:

| 뷰 | 답하는 질문 |
|---|---|
| **키워드 레이더** | 어떤 **게시물**이 지금 터지고 있는가 |
| **경쟁사 모니터링** | 누가 **지속적으로** 히트를 내고 있는가 (계정 단위 집계 + 지속도 계층) |
| **관심 목록** | **내가 지켜보는 사람** 중 누가 새로 올렸는가 |

모든 뷰에서 현재 필터링된 결과를 그대로 CSV로 내보낼 수 있습니다 (Excel에서 바로 열림).

### 주요 특징

- **진짜 실시간**: 상주 프로세스가 일정 간격으로 수집하고, 페이지는 SSE로 푸시를 받습니다. 수집이 끝나는 즉시 순위표가 갱신되며 수동 클릭이 필요 없습니다
- **4가지 참여 지표 완비**: 좋아요 / 답글 / 리포스트 / 인용. 공식 API로는 얻을 수 없습니다
- **썸네일 포함**: 목록 / 카드 / 상세 세 곳에서 이미지를 보여주고, 각 게시물이 텍스트 전용 / 단일 이미지 / 캐러셀 / 동영상인지 표시합니다 — 버즈 판단을 위해 하나씩 열어볼 필요가 없습니다
- **상승 속도를 별도 열로**: `인게이지먼트 / 시간`. "누적이 많은" 것이 아니라 "지금 오르는" 것을 봅니다
- **인게이지먼트 성장 곡선**: 수집할 때마다 스냅샷을 기록하므로 게시물의 성장 추이를 상세 드로어에서 볼 수 있습니다
- **채널 상태 점검 + 서킷 브레이커**: 실패를 실제 원인별로 분류하고, 빈 사이클이 반복되면 차단된 출구를 계속 두드리지 않고 모니터링을 중단합니다
- **의존성 제로**: `urllib` / `sqlite3` / `http.server` / `threading`만 사용. 장시간 가동 시 환경 변화로 깨지지 않습니다
- **5개 언어 UI**: 간체 중국어 / English / 번체 중국어 / 日本語 / 한국어. 내비게이션 바 우측 상단에서 한 번에 전환하고 선택은 브라우저에 저장됩니다. 데이터 측 값(그룹 이름, 키워드, 계정 이름, 게시물 본문)은 번역하지 않습니다 — 화면에서 본 단어를 그대로 설정 파일에서 검색할 수 있게 하기 위해서입니다
- **3단계 반응형**: 데스크톱 / 태블릿 / 모바일. 54가지 너비×뷰 조합에서 가로 스크롤이 없음을 실측했습니다

## 빠른 시작

**Python 3.10 이상**이 필요합니다. `pip install`은 필요 없습니다 (서드파티 의존성 제로).

```
start.bat 더블클릭
```

또는:

```bash
python server.py
```

그런 다음 브라우저에서 **http://127.0.0.1:8650** 을 엽니다.

시작 시 첫 번째 수집 사이클이 즉시 실행되고, 이후 설정한 간격으로 자동 반복됩니다.

### 먼저 threads.com 접속 확인

여기가 **유일하게 막히기 쉬운 지점**입니다. 프로그램은 Python 표준 라이브러리 `urllib`로 수집하며,
`urllib`은 시스템의 `http_proxy` / `https_proxy` 환경 변수를 자동으로 읽습니다.
따라서 직접 연결이 안 되면 아래 방법 중 하나로 프록시를 설정하면 됩니다.

**방법 1: `.env`에 작성** (권장, 프로젝트와 함께 이동)

```bash
cp .env.example .env          # Windows: copy .env.example .env
```

그런 다음 `.env`를 편집하여 주석을 해제하고 본인의 포트로 변경합니다:

```env
http_proxy=http://127.0.0.1:7890
https_proxy=http://127.0.0.1:7890
```

**방법 2: 시스템 환경 변수로 설정** (Windows 명령줄에서 임시 적용)

```bat
set http_proxy=http://127.0.0.1:7890
set https_proxy=http://127.0.0.1:7890
```

> 포트 찾는 법: Clash / v2rayN 등 클라이언트의 "HTTP 포트" 또는 "혼합 포트".
> **`socks5://`를 쓰지 마세요** —— `urllib`은 socks 프록시를 지원하지 않으므로 HTTP 포트를 써야 합니다.

설정 후 화면 오른쪽 위의 **채널 자가진단**(`POST /api/probe`)으로 검증하거나,
명령줄에서 바로 확인할 수 있습니다:

```bash
python -c "from collector import probe_channel; print(probe_channel())"
```

> ⚠️ 수집하려면 프록시가 반드시 켜져 있어야 합니다. 끄면 채널이 502(`proxy_tunnel_502`)를 반환합니다.
> 문제를 볼 때는 먼저 `baidu.com` / `api.github.com`과 비교하세요. 이 둘은 되고 `threads.com`
> 만 안 되면 → 출구가 Meta의 레이트 리밋 대상(빈도를 낮추면 약 20분 후 회복), 셋 다 안 되면 → 프록시 자체 장애입니다.
> 채널 상태와 실패 원인은 화면 상단 경고 바에 표시됩니다.

## 배포 / 다른 사람에게

**이 프로젝트는 "개인용 실시간 모니터링 콘솔"이며 공개 서비스가 아닙니다.** 기본적으로 `127.0.0.1`만 수신합니다.
다른 사람에게 쓰게 하는 가장 간단한 방법은 상대가 clone해서 직접 실행하는 것입니다.

```
git clone https://github.com/BaYue-SYJ/threads-ai-radar.git
cd threads-ai-radar
# 프록시 설정 (위 절 참조)
start.bat            # 또는 python server.py
```

세 가지 유의사항:

1. **의존성을 설치할 필요가 없습니다.** Python만 있으면 됩니다. 데이터베이스 `data/radar.db`는 첫 실행 시 자동 생성됩니다.
2. **각 기기가 각자의 데이터를 수집합니다.** 이 프로그램에는 계정 체계도, 데이터 동기화도 없습니다.
   두 사람이 같은 순위표를 보려면 같은 기기에 접속하세요 (다음 항목 참조).
3. **공용 네트워크에 그대로 노출하지 마세요.** HTTP 서비스에는 인증이 전혀 없어
   포트에 접근 가능한 누구나 키워드와 관심 목록을 바꿀 수 있습니다. LAN 공유가 필요하면 내부 주소에만 바인딩하세요:

   ```env
   RADAR_HOST=0.0.0.0        # 또는 .env에 구체적 내부 IP 지정 (예: 192.168.1.10)
   ```

   그런 다음 방화벽으로 출발지 IP를 제한하세요. **공용 인터넷으로의 포트 포워딩은 하지 마세요.**

### `tools/` 디렉터리 (선택)

`tools/`에 있는 것은 제가 이 프로젝트를 수정할 때 쓴 **회귀 테스트 스크립트**입니다. 실행하려면 Node가 별도로 필요합니다:

| 스크립트 | 역할 | 의존성 |
|---|---|---|
| `check_e2e.cjs` | E2E 회귀: 관심 목록 추가/삭제, 별표, 양방향 이동, CSV 내보내기를 모두 점검 (39개 어서션) | puppeteer-core |
| `check_watch.cjs` | 반응형 스캔: 18개 너비 × 3개 뷰 = 54개 조합에서 가로 오버플로와 JS 오류 확인 | puppeteer-core |
| `shots3.cjs` | 3개 뷰 자동 스크린샷 (데스크톱 1440 / 태블릿 1024 / 모바일 390) | puppeteer-core |
| `scan_broken_modules.cjs` | `node_modules`에서 "패키지는 있지만 진입 파일이 사라진" 손상된 패키지 탐지 | **없음** |
| `verify_i18n_static.cjs` | 다국어 사전 정적 검증: 5개 언어 키 집합 일치, 플레이스홀더 정합, 참조 키 존재, 고아 키/빈 번역 없음 | **없음** |
| `verify_i18n.cjs` | 다국어 E2E 검증: 실제로 페이지를 열어 5개 언어를 차례로 전환하며 표 헤더/카드/상태 표시줄/빈 상태, 키 이름 누출 없음, 데이터가 번역되지 않음을 확인 (65개 어서션) | jsdom |
| `i18n_sample.cjs` | 언어별 UI 문구를 추출해 번역 품질을 눈으로 확인 | jsdom |
| `verify_readmes.cjs` | 5개 README 일관성: 내부 앵커, 제목/표 구조, 언어 전환 상호 링크, 5개 언어 완비 | **없음** |

**도구로만 쓴다면 이 디렉터리는 신경 쓸 필요가 없습니다.** 회귀 테스트를 돌리려면:

```bash
npm i -D puppeteer-core jsdom
node tools/check_watch.cjs          # 서버를 먼저 실행해야 함
node tools/verify_i18n_static.cjs   # 서버 불필요, 밀리초 단위
node tools/verify_i18n.cjs          # 서버를 먼저 실행해야 함
node tools/verify_readmes.cjs       # 서버 불필요
```

스크립트는 Chrome을 자동으로 탐지합니다. 찾지 못하면 `CHROME_PATH` / `PUPPETEER_PATH`로 지정하세요.

## 데이터를 어떻게 가져오는가

프로젝트 전체에서 가장 중요한 점이므로 먼저 분명히 밝힙니다.

**공식 Threads API는 사용할 수 없습니다:** `keyword_search`는 Meta App Review 통과가 필요하고, 승인 전에는 자신이 올린 게시물만 반환합니다. 게다가 응답에 **좋아요 / 답글 / 리포스트 / 인용 네 가지 수치가 아예 포함되지 않습니다**. 인게이지먼트를 얻을 수 없는 "버즈 레이더"는 존재하지 않는 것과 같습니다.

**실제로 채택한 방식: Googlebot UA + 서버 사이드 렌더링.**

| 요청 방식 | 반환 내용 |
|---|---|
| 일반 브라우저 UA | 약 275KB의 SPA 빈 껍데기, **게시물 데이터 전혀 없음** |
| `Googlebot` UA | **1.0~1.9MB의 완전한 SSR 페이지**, 게시물 데이터가 인라인 JSON으로 포함 |

로그인 불필요, OAuth 불필요, App Review 불필요, 비용 제로. 네 가지 인게이지먼트 지표를 모두 얻을 수 있습니다.

### 필드 위치 (코드를 수정할 때 가장 많이 밟는 함정)

네 가지 지표는 **같은 계층에 있지 않습니다**:

| 필드 | 위치 |
|---|---|
| `like_count` | 게시물 객체의 **최상위** |
| `direct_reply_count` | `text_post_app_info` 안. **`reply_count`라는 이름이 아님에 주의** |
| `repost_count` | `text_post_app_info` 안 |
| `quote_count` | `text_post_app_info` 안 |

어떤 객체가 게시물인지 판정하려면 조건에 `code` + `like_count` + `text_post_app_info`를 **동시에** 포함해야 합니다.
앞의 두 개만 쓰면 **바깥 계층에서 멈춰 더 내려가지 않고**, 나머지 세 필드를 모두 0으로 읽게 됩니다——개발 중 실제로 한 번 밟았던 함정입니다.

## 키워드 작성법

`keywords.txt`를 편집하거나, 화면 상단의 "모니터링 키워드" 패널에서 직접 추가/삭제합니다.

```
[모델]                    ← 대괄호는 그룹. 화면의 카테고리로 그대로 사용됩니다
ChatGPT | GPT | chatgpt   ← 세로줄은 동의어 구분
AI prompt                 ← 공백 = AND
```

- **공백 = AND**: `AI prompt`는 본문에 AI와 prompt가 모두 있어야 함
- **세로줄 = OR**: `ChatGPT | GPT`는 어느 하나만 맞아도 관련으로 판정.
  **검색에 쓰는 것은 첫 번째 표기뿐**이고, 뒤의 것은 판정에만 사용됩니다. 많은 게시물이 정식 명칭 대신 `GPT`만 쓰므로 동의어를 넣어야 놓치지 않습니다.
- 해시태그 붙여쓰기도 자동 호환: `#aiprompt`도 `AI prompt`에 일치합니다
- `ai` 같은 짧은 단어에는 근사 단어 경계 매칭을 사용하므로 `said` / `available`을 잘못 잡지 않습니다

## 관련성 필터

Threads 검색은 **의미 기반 리콜**이며, "본문에 그 단어가 포함되는" 리콜이 아닙니다. 실측으로 `AI prompt`를 검색하면 인도네시아어 트래픽 유도 게시물, 심지어 AI 규제를 언급한 정치인 게시물(좋아요 11,168로 1위)까지 반환됩니다.

그래서 매 수집 사이클 후 게시물에 판정을 부여합니다:

| 판정 | 의미 |
|---|---|
| **관련** | 본문이 키워드 구문, 또는 모든 유효 단어, 또는 동의어에 일치 |
| **무관** | 검색에 의해 수집되었으나 본문이 키워드와 무관 |
| **차단** | `blocklist.txt`의 노이즈 단어에 일치 |

화면의 "**관련만 보기**" 스위치로 뒤의 두 종류를 표시할지 제어합니다 (기본 켜짐).

**관련률은 구조적으로 낮아 실측 약 4%**입니다——이는 Threads 검색의 고유 특성이며 버그가 아닙니다.
본 기기에서 누적 16,710건을 수집해 그중 관련 730건(**4.4%**, 2026-09-15 기준).
극단적 예: `Nano Banana`로 64건을 수집했는데 "banana"를 포함한 것은 **0건**——
전부 인도네시아어 "nano KOL" 마케팅 게시물이었고 필터가 정확히 모두 걸러냈습니다.

> 관련률이 낮다고 쓸모없는 것은 아닙니다. 걸러내는 것은 의미적 노이즈이고, 남는 것은 진짜 히트입니다.
> 커버리지를 높이려면 필터를 완화하기보다 키워드와 변형을 늘리는 것이 효과적입니다.

키워드나 차단어를 바꾼 뒤 기존 데이터를 재판정하려면 (재수집 불필요):

```bash
python refilter.py
```

## 수집 변형 (사실상의 페이지 넘기기)

Threads 검색 페이지의 `serp_type` 파라미터는 **서로 다른 배치**의 결과를 반환합니다. 여러 변형을 가져와 병합·중복 제거하면
페이지 넘기기와 같은 효과를 얻습니다——이는 내부 GraphQL로 커서를 얻는 것보다 안정적입니다 (실측상 GraphQL 채널은 실제 브라우저
세션의 cookie + csrf가 필요하고, 직접 POST하면 HTML 껍데기만 반환됩니다. 게다가 doc_id는 교체됩니다).

**⚠️ 변형 선택은 "관련 게시물 산출"로 봐야 하며 "원시 건수"로 판단할 수 없습니다——둘의 차이가 매우 큽니다.**

각 변형이 새로 만들어내는 **관련 게시물** 수 (base 기준 실측):

| 키워드 | base | recent | top | tag | **profile** | **default** |
|---|---|---|---|---|---|---|
| ChatGPT | 15 | +0 | +0 | +0 | **+17** | +9 |
| Nano Banana | 3 | +0 | +2 | +1 | **+13** | +7 |
| AI prompt | 21 | +6 | +0 | +1 | +0 | **+10** |

`recent`는 원시 건수가 크게 늘지만 **거의 전부 의미적 노이즈**입니다. 진짜 가치는 `profile`과 `default`에 있습니다.
저는 처음에 원시 건수로 `base,recent,top`을 골랐고, 결과적으로 가장 약한 두 변형을 선택하고 있었습니다——관련 게시물 산출로 다시 고른 뒤에야 실제 효과를 얻었습니다.

3개 변형 실측 효과:

| | 단일 변형 | 3개 변형 | 개선 |
|---|---|---|---|
| 라이브러리 총수 | 980 | **3,865** | 3.9× |
| **관련 게시물** | 136 | **415** | **3.1×** |
| 커버 계정 | 941 | 3,562 | 3.8× |
| 사이클 소요 시간 | 약 2분 | 약 7분 | 3.5× |

### ⚠️ 변형 수는 차단 위험과 직결됩니다 (실측 경험)

3개 변형 × 19개 키워드 = **사이클당 57 요청**. 3사이클을 돌리자 `threads.com`이 본 기기 출구에 반환하기 시작했습니다:

```
urllib.error.URLError: Tunnel connection failed: 502 Bad Gateway
```

동시에 `baidu.com`, `api.github.com`은 여전히 200 —— 즉 **프록시 장애도, Threads 장애도 아니고** 출구 IP가 Meta의 레이트 리밋을 받은 것입니다. 약 20분 후 자연 회복되었습니다.

결론: **장시간 가동 시 변형은 2개 이내**(기본 `base,profile`), 간격은 30분 이상으로 늘리세요. 제한 후 유일하게 효과 있는 회복 수단은 부하를 낮추고 일정 시간 멈추는 것입니다. 무리한 재시도는 차단을 연장시킬 뿐입니다.

> 이런 문제는 반드시 채널을 나눠 검증해야 합니다. `baidu.com` / `api.github.com`과 비교해야 "프록시 전체 장애"와 "특정 대상 레이트 리밋"을 구분할 수 있습니다.

## 실시간 모니터링 동작 방식

`server.py`는 시작 시 프로세스 내부에서 백그라운드 스케줄러 스레드를 띄웁니다:

- 고정 간격(기본 15분)으로 모든 키워드를 순회 수집
- 키워드 사이에 1.8~4.2초의 **무작위 지터**를 삽입해 일정한 리듬으로 레이트 리밋을 유발하는 것을 회피
- 페이지는 **SSE**(`/api/stream`)로 푸시를 받고 2초마다 상태를 동기화하며, 수집 완료 시 즉시 순위표를 갱신
- 수집할 때마다 `snapshots` 테이블에 인게이지먼트 스냅샷을 기록해 상세 드로어에서 상승률 곡선을 볼 수 있습니다

화면에서 볼 수 있는 것:

- 내비게이션 바 상태 점: **모니터링 중 / 수집 중 / 일시정지 / 채널 이상**
- 다음 수집까지 **카운트다운**
- 수집 진행 바 `7/19 · Midjourney`
- 스크롤되는 수집 로그 (이상 경고 포함)
- 새로 저장된 게시물의 **NEW** 배지

세 뷰 모두 데스크톱 / 태블릿 / 모바일을 지원합니다. **18개 너비(390~1680px) × 3개 뷰 = 54개 조합에서 가로 오버플로가 없음을 실측**했습니다:

>
> 또 하나의 함정: **`getBoundingClientRect().right > clientWidth` 오버플로 감지는 닫힌 드로어를 모두 오버플로로 계산합니다**

> 더 신뢰할 수 있는 판정은 `documentElement.scrollWidth > clientWidth`입니다.

### 상태 점검과 채널 자가진단

수집할 때마다 "응답 크기 ≥ 400KB이고 게시물 ≥ 5건을 파싱했는가"를 검증하고, 못 미치면 이상으로 표시합니다.

하지만 크기 검사만으로는 부족합니다——**"가져왔지만 페이지에 데이터가 없음"과 "경로 자체가 안 뚫림"은 다른 문제**입니다. 전자는 수집기를 재시작하면 되지만,
후자는 무리한 재시도가 레이트 리밋을 악화시킬 뿐입니다. 그래서 실패를 구체적 원인으로 분류합니다:

| reason | 의미 | 대처 |
|---|---|---|
| `proxy_tunnel_502` | 프록시 터널 502, 출구 거부 | 빈도 낮추기 + 일정 시간 중단 |
| `rate_limited` | HTTP 429 레이트 리밋 | 변형 수 줄이고 간격 늘리기 |
| `connect_timeout` | 직접 연결 차단 | 사용 가능한 프록시 경유 |
| `tls_reset` | TLS가 중간 장비에 의해 리셋 | 경로 변경 |
| `gateway` | 업스트림 5xx | 보통 자연 회복 |
| `empty_shell` | 페이지는 받았으나 SSR 없음 | UA가 강등됨. `RADAR_USER_AGENT` 변경 여부 확인 |

내비게이션 바의 "**자가진단**"을 누르거나 `/api/probe`를 호출하면 **요청 1개만** 보내 채널 상태를 빠르게 판정합니다. 사이클 전체를 기다릴 필요가 없습니다.

![채널 이상 경고 바](docs/channel-alert.png)

위 이미지는 출구가 레이트 리밋을 받은 실제 화면입니다. 상단 빨간 바가 **구체적 원인**(`proxy_tunnel_502`)과
**실행 가능한 조치**(일정 시간 후 재시도, 또는 변형 수 줄이기)를 제시합니다. 로그에 "페이지 이상" 한 줄만 남기지 않습니다.
내비게이션 바 상태 점도 동시에 "채널 이상"으로 바뀝니다.

### 서킷 브레이커

**한 사이클이 완전히 비면**(19개 키워드에서 하나도 못 가져옴) 개별 키워드의 데이터 부족이 아니라 채널 장애로 판단합니다.
이것이 **3사이클** 계속되면 **모니터링을 자동 일시정지**하고 로그에 이유를 남깁니다——차단된 출구를 일정 간격으로 계속 두드리는 것을 피하기 위해서입니다.

화면 상단에 빨간 경고 바가 뜨며 이유와 대처를 제시합니다. 로그에 "페이지 이상" 한 줄만 남기지 않습니다.

### 사이클 전체 워치독

한 사이클 수집에는 **엄격한 시간 상한**이 있습니다(`RADAR_CYCLE_MAX_SECONDS`, 기본 1800초 = 30분).
시간이 되면 해당 사이클을 중단하고, 몇 번째 키워드에서 멈췄는지, 왜인지를 로그에 기록합니다.

왜 필요한가: **노트북 절전은 수집 스레드를 통째로 얼립니다.** 실측으로 7번째 키워드를 처리한 뒤 기기가 절전에 들어갔고,
스레드가 **15.5시간** 동안 그 자리에서 돌아오지 않았습니다 (절전을 넘나들면 단일 요청의 socket 타임아웃이 듣지 않을 수 있습니다).
그동안 다음 사이클 수집이 계속 막혀 있었습니다. 워치독은 각 키워드 시작 전에 타임아웃을 확인하고, 복귀 후 즉시 마무리 종료하므로
다음 사이클이 정상적으로 시작됩니다.

중간에 중단되면 `keywords_done`은 **실제 완료된 건수**를 그대로 기록합니다(예: `9/19`).
"이번 사이클 전부 완료"라고 거짓 보고하지 않습니다.

### 중단 잔여 레코드 자동 정리

프로세스가 강제 종료(또는 워치독 중단)되면 수집 레코드가 `running`에 멈춥니다. 시작 시 자동으로 훑어
이런 레코드를 `error / 프로세스 중단, 이번 사이클 미완료`로 표시합니다——그러지 않으면 화면이 계속 "수집 중"으로 표시되어
도구가 멈춘 것처럼 보입니다.

## 경쟁사 / 동종업계 모니터링

키워드 순위가 답하는 것은 "**어떤 게시물이 터졌는가**". 동종업계 순위가 답하는 것은 "**누가 지속적으로 히트를 내는가**"입니다.
후자는 작성자 단위 집계가 필요하며, 여기가 이 프로젝트의 진짜 차별점입니다——경쟁사 분석에서 봐야 할 것은 사람과 방법론이지 단일 게시물이 아닙니다.

화면 상단 두 번째 탭 "**경쟁사 모니터링**"에서 관련 게시물을 작성자 단위로 집계합니다:

- **계층**: 지속도로 자동 라벨링. 이것이 모니터링 대상을 고르는 근거입니다

  | 계층 | 조건 | 의미 |
  |---|---|---|
  | 핵심 모니터링 | 게시물 ≥ 3 이고 히트 ≥ 2 | 방법론이 안정적, 장기 추적 가치 있음 |
  | 지속 산출 | 게시물 ≥ 2 | 안정적 산출이 있음 |
  | 단발 히트 | 게시물 = 1 이고 히트 ≥ 1 | 우연일 수 있음 |
  | 산발 등장 | 그 외 | 일회성 등장 |

  (히트 = 단일 게시물 인게이지먼트 합계 ≥ 500, 임계값은 `store.HIT_THRESHOLD`)

- **각 행 표시**: 관련 게시물 수, 히트 수, 히트율, 총 인게이지먼트, 게시물당 평균, 최고 점수, 주력 분야, 최근 활동
- **아무 계정이나 클릭**하면 드로어가 열립니다: 계층, 게시 빈도(약 N건/주), 주력 분야, 일치 키워드, 해당 계정의 모든 관련 게시물
- **정렬**: 히트 수 / 관련 게시물 수 / 총 인게이지먼트 / 게시물당 평균 / 히트율 / 최고 점수 / 최고 좋아요 / 이번 사이클 신규

### "지속도" 필터가 반드시 필요한 이유

데이터가 적을 때는 대부분의 계정이 한 번만 등장합니다. 첫 사이클 391명 작성자 실측:

```
게시물 ≥ 1: 391        게시물 ≥ 2: 14        게시물 ≥ 3: 5
계층 분포: 핵심 모니터링 1 / 지속 산출 13 / 단발 히트 50 / 산발 등장 327
```

**계정의 96%가 "일회성 등장"**입니다. 히트 수로 그대로 정렬하면 순위표가 단발 작성자로 가득 차 누구를 장기적으로 봐야 할지 전혀 알 수 없습니다.
그래서 "지속 산출만 보기(≥2 게시물)" 스위치를 기본 제공하고, 계층마다 기본 정렬 필드를 설정했습니다.

화면 상단에 샘플 두께가 표시되어, "지속 산출" 인원이 적은 이유가 수집 사이클이 아직 부족해서이지 기능이 고장 나서가 아님을 알 수 있습니다.
**여러 번 돌려야 이 순위표가 진짜 정보량을 갖습니다**——계정 축이 시간 누적을 필요로 하는 이유입니다.

## 관심 목록

동종업계 순위는 "사이트 전체를 훑은 순위", 관심 목록은 "**내가 직접 골라 지켜볼 사람**"입니다. 이 둘은 다른 화면이 필요합니다:
전자는 넓이와 정렬을 통한 규칙 발견이, 후자는 짧음과 "누가 새로 올렸는가"의 즉각성이 필요합니다.

세 번째 탭 "**관심 목록**". 세 가지 경로로 추가할 수 있습니다:

- 경쟁사 모니터링 화면의 각 행/카드 왼쪽 **☆** 로 원클릭 등록 (테이블·카드 뷰 모두 지원)
- 관심 목록 화면 상단 입력란. `@xxx`, `xxx/`, 프로필이나 게시물 URL을 그대로 붙여넣기 가능
- `watchlist.txt` 직접 편집. 형식은 `계정 | 메모`, 재시작 시 자동으로 읽어들임

등록 후:

- **새 게시물이 있는 사람이 맨 위로**, `+N` 파란 배지가 붙습니다. 상단에 "등록 N개 / 새 글 있음 N개 / 새 게시물 총 N건" 표시
- "새 글만 보기" 스위치, 그리고 이번 사이클 신규 / 총 인게이지먼트 / 히트 수 / 관련 게시물 수 / 최근 활동 정렬 지원
- 메모는 항상 표시(테이블에서는 독립 열). "이 사람이 주로 무엇을 하는지" 적는 데 계정명보다 유용합니다
- 계정명을 클릭하면 같은 드로어가 열려 모든 관련 게시물을 볼 수 있고, 드로어에서 바로 등록/해제도 가능
- 목록은 `watchlist.txt`에 동기화되어 다시 기록됩니다. **DB가 원본, 파일은 미러**이므로 파일이 화면 조작으로 깨지지 않습니다

> 등록은 "골라서 지켜보기"일 뿐, **수집 스위치가 아닙니다**. 계정이 먼저 키워드에 걸려 DB에 들어와야 데이터가 있습니다.
> 아직 DB에 없는 계정은 `has_posts=false`와 0들을 표시할 뿐, 목록에서 사라지지는 않습니다——
> 사라지면 사용자가 등록이 안 된 것으로 오해합니다.

### 게시물 ⇄ 계정 양방향 이동

게시물 상세 드로어에는 "@xxx의 모든 관련 게시물 보기 →"가 있고, 계정 드로어에서 아무 게시물이나 클릭하면 게시물 상세로 돌아옵니다.
두 방향 모두 **같은 드로어의 내용을 교체**하는 방식이라 라우트를 쌓지 않으므로, 왕복해도 히스토리 스택 충돌이 없습니다.

![계정 상세 드로어](docs/author-drawer.png)

계정 드로어는 해당 계정의 상황을 한 번에 펼칩니다: 관련 게시물 수, 히트 수, 총 인게이지먼트, 평균 인게이지먼트, 주력 분야,
일치 키워드, 그리고 모든 관련 게시물 목록. 오른쪽 위의 **★ 이 계정 등록**으로 관심 목록에 원클릭 추가할 수 있고,
이후 "관심 목록" 탭에서 새 글을 지켜볼 수 있습니다.

## CSV 내보내기

세 뷰 각각에 "CSV 내보내기" 버튼이 있습니다 (키워드 레이더 / 경쟁사 모니터링 / 관심 목록).

내보내는 것은 **지금 화면에 보이는 그대로**——필터, 검색어, 정렬이 모두 반영됩니다.
필터링한 뒤 내보냈는데 전체가 나오는 것은 가장 비판받기 쉬운 불일치입니다.

Excel을 위한 두 가지 세부 배려가 있고, 하나라도 빠지면 중국어가 깨집니다:

- 맨 앞에 UTF-8 BOM(`\ufeff`)을 씁니다. 쓰지 않으면 Excel이 GBK로 해석해 중국어 열이 모두 깨집니다
- 줄바꿈을 `\r\n`으로 통일. 메모장과 Excel 모두 표 전체를 한 줄로 뭉개지 않습니다

서버 측에는 별도로 `/api/export`가 있으며(아래 참조), 동일한 BOM/CRLF 형식을 반환합니다.
대량 내보내기와 스크립트 호출에 적합하며, 브라우저 메모리의 3000건 제한을 받지 않습니다.

### HTTP API

| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | `/api/status` | 실행 상태: 진행, 다음 수집, 채널 상태, 통계, 로그 |
| GET | `/api/posts?limit=&only_relevant=` | 게시물 목록 |
| GET | `/api/post/<code>` | 단일 게시물 상세 + 인게이지먼트 성장 곡선 |
| GET | `/api/authors?min_posts=&tier=&sort=&limit=` | **동종업계 순위**, `coverage` 샘플 두께 포함 |
| GET | `/api/author/<username>` | **특정 계정의 관련 게시물 목록** |
| GET | `/api/watchlist` | **관심 목록**, 각 계정의 실시간 집계와 `summary` 포함 |
| GET | `/api/export?what=posts\|authors&only_relevant=&limit=` | **CSV 내보내기** (UTF-8 BOM + CRLF, Excel에서 바로 열림) |
| GET | `/api/keywords` | 키워드 표 |
| GET | `/api/runs` | 수집 이력 |
| GET | `/api/stream` | SSE 실시간 푸시 (상태 / 로그 / 진행) |
| POST | `/api/collect` | 즉시 수집 |
| POST | `/api/pause` · `/api/resume` | 일시정지 / 재개 |
| POST | `/api/interval` | 수집 간격 변경 (`{"minutes": 30}`) |
| POST | `/api/probe` | **채널 자가진단** (요청 1개로 경로 가용성 판정) |
| POST | `/api/keywords` | 키워드 추가 |
| POST | `/api/watchlist` | **등록** (`{"username":"@xxx","note":"메모"}`, 계정명 정규화됨) |
| POST | `/api/seen` | 모든 NEW 표시 제거 |
| DELETE | `/api/keywords?keyword=` | 키워드 삭제 |
| DELETE | `/api/watchlist?username=` | **등록 해제** |

`/api/watchlist`의 계정명은 정규화됩니다: `@Xxx`, `https://www.threads.com/@Xxx/?hl=zh`,
`threads.net/@Xxx/`는 모두 소문자 `xxx`로 통일됩니다. 정규화하지 않으면 `@SomeOne`과 `someone`
이 목록에서 두 줄이 됩니다.

`/api/posts`와 `/api/post/<code>`의 각 항목에는 다음 미디어 필드가 붙습니다:
`media_type` (`19`=텍스트 전용 / `1`=단일 이미지 / `8`=캐러셀 / `2`=동영상),
`has_image` (해당 게시물에 이미지가 있는지), `thumb` (썸네일 URL, 없으면 `null`).
**동영상 게시물의 `media_type`은 `2`이지만 썸네일에는 커버 프레임이 들어갑니다**——즉 "이미지 있음"이 "이미지 게시물"은 아니므로
게시물 유형 판정은 `media_type`으로 해야 합니다.

`/api/authors`의 `sort` 선택지: `hits` / `posts` / `interactions` / `avg_interactions` /
`hit_rate` / `best_score` / `best_likes` / `new_count`. 미지정 시 계층별 기본값——
핵심/지속 계층은 히트 수와 산출량, 단발 계층은 단일 게시물 영향력을 봅니다.

`/api/export`의 `limit` 상한은 20000(기본 5000). `what`은 `authors`만 인식하고 나머지는 `posts`로 처리합니다.

## 점수 계산

점수 공식은 아래와 같으며, 네 가지 인게이지먼트 지표는 모두 실제 데이터에서 가져옵니다:

```
점수 = (1.0·ln(좋아요) + 2.5·ln(답글) + 3.0·ln(리포스트) + 3.0·ln(인용))
       × AI 관련도 가중(1.25 / 1.0)
       × 시간 감쇠(1/√(1+시간/24))
```

추가로 **상승 속도** = 인게이지먼트 / 시간을 별도로 둡니다. 버즈 레이더에서 진짜 봐야 할 것은 "지금 오르는" 게시물이며,
"누적이 많은" 오래된 게시물이 아니므로 정렬에 독립 항목으로 넣었습니다.

## 설정

`.env.example`을 `.env`로 복사한 뒤 필요에 따라 수정합니다. 모두 기본값이 있습니다.
**화면에서 수집 간격을 바꾸면 `.env`에 자동으로 다시 기록**되므로 재시작해도 유지됩니다.

> 프록시(`http_proxy` / `https_proxy`)도 `.env`에 씁니다. 설정 방법은
> 위 [먼저 threads.com 접속 확인](#먼저-threadscom-접속-확인)을 참조하세요.

자주 바꾸는 항목:

```env
RADAR_INTERVAL_MINUTES=30          # 수집 간격 (분)
RADAR_PORT=8650                    # 서비스 포트
RADAR_SERP_TYPES=base,profile      # 수집 변형. 많을수록 넓지만 레이트 리밋을 받기 쉬움
RADAR_CYCLE_MAX_SECONDS=1800       # 사이클 시간 상한 (워치독)
RADAR_FAILURE_LIMIT=3              # 빈 사이클이 몇 번 반복되면 차단할지
```

> ⚠️ `RADAR_USER_AGENT`는 바꾸지 마세요. 일반 브라우저 UA로 바꾸면 빈 껍데기 페이지가 반환되어 수집이 완전히 무효화됩니다.

## FAQ

**페이지는 열리는데 데이터가 하나도 없음 / 계속 수집 실패로 표시됨.**

먼저 상단 경고 바의 `reason`을 보세요. 가장 흔한 두 가지:

- 본 기기에서 프록시를 켜지 않음 → `threads.com` 직접 연결 불가 (중국 내에서는 기본 상황입니다)
- 프록시는 켜져 있지만 출구가 Meta의 레이트 리밋 대상(`proxy_tunnel_502`) → 수집 빈도를 낮추고 약 20분 후 회복을 기다림

내비게이션 바의 "**자가진단**"을 누르면 사이클 전체를 기다리지 않고 요청 1개로 채널을 판정할 수 있습니다.

**"프록시 장애"와 "Threads만 레이트 리밋"을 어떻게 구분하나?**

`baidu.com` / `api.github.com`과 비교하세요: 이 둘은 되고 `threads.com`만 안 되면 → 출구 레이트 리밋.
셋 다 안 되면 → 프록시 자체 문제입니다. **이 구분이 중요합니다.** 그러지 않으면 코드에서 헛되이 시간을 소모합니다.

**포트 8650이 사용 중입니다.**

`.env`의 `RADAR_PORT`를 바꾸거나, 임시로 환경 변수 `set RADAR_PORT=8660`을 설정하세요.

**관련 게시물이 너무 적습니다.**

Threads 검색은 의미 기반 리콜이므로 관련률이 구조적으로 4~5%밖에 안 됩니다. 이는 플랫폼 특성이지 버그가 아닙니다.
커버리지를 높이는 가장 효과적인 방법은 필터를 완화하는 것이 아니라 **키워드 추가**와 **변형 추가**(`RADAR_SERP_TYPES`)입니다——
완화하면 노이즈만 늘어납니다.

**동종업계 순위에서 대부분의 계정이 한 번만 나옵니다. 의미 없어 보입니다.**

정상입니다. 첫 사이클에는 96%의 작성자가 관련 게시물을 1건만 올렸습니다. 지속 산출 순위는 **십수 사이클**의 수집이 있어야 형성됩니다.
며칠 돌려놓고 다시 보면 완전히 달라집니다.

**`keywords.txt`를 바꿨는데 기존 데이터의 분류가 안 바뀝니다.**

키워드는 **신규 수집**의 판정에만 영향을 줍니다. 기존 데이터를 새 키워드로 재계산하려면:

```bash
python refilter.py
```

**데이터는 어디에 저장되나요? 백업 / 이전은?**

모두 `data/radar.db` 하나의 SQLite 파일에 있습니다. 복사하면 됩니다(`-wal`도 함께 복사하면 더 안전합니다).
기기를 옮길 때는 `.env`도 함께 가져가세요(변경한 간격 등 설정이 들어 있습니다).

**X / Instagram / 샤오홍슈도 모니터링할 수 있나요?**

아니요, 이 프로젝트는 Threads만 다룹니다. 다른 플랫폼은 수집 로직이 완전히 달라 설정 변경으로 해결되지 않습니다.

**수집이 제 Threads 계정에 영향을 주나요?**

**아니요.** 이 프로젝트는 로그인이 필요 없고 공개 검색 페이지 + Googlebot UA를 사용하며 여러분의 계정을 전혀 건드리지 않습니다.
다만 **출구 IP는 레이트 리밋을 받습니다**: 실측으로 3개 변형 × 19개 단어를 3사이클 돌리면 502가 됩니다(약 20분 후 회복).
장시간 가동 시 변형 ≤2, 간격 ≥30분을 권장합니다.

**화면에 게시물 이미지가 표시되나요?**

현재 버전은 표시됩니다. 자세한 내용은 아래 [알려진 제한 #10](#알려진-제한)을 참조하세요. 수정된 결함이지만
**기존 오래된 게시물의 썸네일은 다시 수집되기를 기다려야 합니다.**

## 알려진 제한

1. **진짜 페이징 커서가 없습니다.** "다중 변형 수집"으로 대체했습니다(위 참조). 키워드당 약 110~130건의 중복 제거 결과를 얻고 관련 게시물 산출이 3.1배가 되었습니다. 진짜 페이징을 하려면 내부 GraphQL의 doc_id와 실제 브라우저 세션이 필요하고 비용이 크며 doc_id도 교체됩니다.
2. **관련률이 구조적으로 낮음**: 본 기기에서 누적 16,710건을 실측해 관련은 730건으로 약 **4.4%**
   (2026-09-15 기준). Threads 검색은 의미적 매칭이라 한 단어만 스친 대량의 게시물을 끌고 옵니다
   (예: `AI art` 검색 시 art를 언급한 온갖 내용이 반환됨). 키워드와 변형 수를 늘리는 것이
   필터 조정보다 커버리지 향상에 효과적입니다.
3. **인게이지먼트가 0인 게시물이 많음**: 롱테일이 많기 때문입니다. 화면의 "최소 인게이지먼트" 슬라이더가 이를 위한 것입니다.
4. **UA 전략은 우회 수단**이며 Meta의 공개 계약이 아닙니다. 언제든 강화될 수 있습니다. **수집 빈도가 너무 높으면 출구가 레이트 리밋을 받습니다**(실측으로 3개 변형을 3사이클 돌려 502, 약 20분 후 회복). 로그 경고 + 채널 자가진단 + 서킷 브레이커가 방어선입니다.
5. **`detected_language`는 신뢰할 수 없음**: 실측으로 관련 게시물의 **81%**가 NULL(전체 DB는 45%).
   언어 필터에 의존할 수 없습니다. 언어로 거르려면 본문 특징을 직접 봐야 합니다.
6. 분류는 `keywords.txt`의 그룹을 사용하며, 일치하지 않는 것은 "미분류"로 들어갑니다.
7. 사이클 소요 시간은 약 2분/변형 × 키워드 수. 키워드 수가 크게 늘면 수집 간격도 함께 늘려야 사이클이 겹치지 않습니다.
8. **동종업계 축은 시간 누적이 필요**. 첫 사이클 391명 작성자 중 관련 게시물이 ≥2건인 사람은 14명뿐이고 나머지 96%는 일회성 등장입니다. "지속 산출" 순위를 의미 있게 만들려면 최소 십수 사이클이 필요합니다.
9. **신규 계정/신규 게시물은 콜드 스타트가 있음**: `velocity`(인게이지먼트/시간)는 첫 수집 시 스냅샷이 1건뿐이라 곡선이 2사이클째에 형성됩니다.
10. **`has_image`가 항상 1, 화면에 이미지가 안 나옴 —— 수정 완료, 다만 기존 썸네일은 재수집 대기 중.**
    실제 버그이며 이번 버전에서 수정했습니다. 다만 **오래된 DB의 기존 데이터가 저절로 생겨나지는 않습니다**. 세 가지로 나눠 설명합니다:

    - **쓰기 로직(수정 완료)**: 원래 판정은 `bool(raw.get("image_versions2"))`였지만, Threads는
      **모든** 게시물(텍스트 전용 포함)에 `image_versions2` 키를 반환합니다.
      텍스트 전용 게시물의 값은 빈 껍데기 `{"candidates": []}`이므로 불리언이 항상 참이 되어
      실측 19,963 / 19,963건 모두 "이미지 있음"으로 표시되었습니다. 현재는
      `bool((raw.get("image_versions2") or {}).get("candidates"))`로 변경했습니다.
      새로 수집한 52건 샘플 교차 검증: `media_type=19`(텍스트 전용) 33건은 **전부** 이미지 없음,
      `1`/`8`/`2`(단일 이미지 / 캐러셀 / 동영상) 19건은 **전부** 이미지 있음으로 100% 일치했습니다.
    - **기존 `has_image`(수정 완료)**: 시작 시 데이터 마이그레이션을 한 번 자동 실행합니다
      (`UPDATE posts SET has_image=0 WHERE media_type=19 AND has_image=1`).
      멱등이며 데이터를 전혀 삭제하지 않습니다. 실측으로 13,247건의 텍스트 전용 게시물을 "이미지 있음"에서 "이미지 없음"으로 되돌려
      19,968건 중 `has_image=1`이 19,966에서 6,719(33.6%)로 줄었습니다.
    - **썸네일(신규 추가, 새 게시물에만 적용)**: `posts` 테이블에 `thumb` 열을 추가하고
      목록 / 카드 / 상세 드로어 세 곳에서 렌더링하며 CSV 내보내기에도 이 열이 포함됩니다.
      다만 **오래된 행의 `thumb`는 비어 있습니다**——당시 URL을 저장하지 않아 복원할 수 없고,
      해당 게시물이 다시 수집될 때 채워지기를 기다려야 합니다(쓰기에 `COALESCE`를 써서 기존의 좋은 데이터를 지우지 않습니다).
      모든 썸네일을 즉시 보고 싶다면 `data/radar.db`를 삭제하고 한 사이클 다시 돌리면 됩니다.
