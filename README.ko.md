## 무엇을 해결하나

Threads의 AI 콘텐츠는 엄청 빠르게 오르는데, **거의 절대 제때 못 봅니다**:

- 공식 API의 `keyword_search`는 **참여 지표를 하나도 주지 않습니다** (좋아요·답글·리포스트 수를 못 가져옴)
- 알고리즘 피드를 넘겨보는 건 키워드 모니터링이 아니라 그냥 먹이를 받는 것
- 어떤 글이 터진 뒤에야 눈에 들어오면, 주제를 잡을 타이밍은 이미 지났습니다

이 도구가 하는 일은 단순합니다: **지정한 키워드를 일정 간격으로 자동 수집하고, 이미지가 있고 반응이 있는 것만 남겨 「지금 오르는 순」으로 정렬**합니다.

크롤링 프레임워크가 아니라, 상시 켜둘 수 있는 단일 프로세스입니다.

## 빠른 시작

### 1. threads.com 접속 가능 여부 확인

브라우저에서 <https://www.threads.com/search?q=ChatGPT> 를 열어 내용이 보이면 됩니다.

**안 열리면**(많은 지역에서 직결이 막혀 있습니다) 프록시가 필요합니다. 이 프로젝트는 Python 표준 라이브러리 `urllib`로 수집하며, 시스템의 `http_proxy` / `https_proxy` 환경 변수를 자동으로 읽습니다:

```bat
set http_proxy=http://127.0.0.1:7890
set https_proxy=http://127.0.0.1:7890
```

프로젝트 루트의 `.env`에 적어도 됩니다 (`.env.example`의 설명 참고).

> ⚠ 프록시 포트는 사용하는 클라이언트의 「믹스드 포트 / HTTP 포트」를 넣으세요. SOCKS 포트가 아닙니다.

### 2. 실행

Windows라면 `start.bat` 더블클릭. 또는 명령줄에서:

```bash
python server.py
```

**`pip install` 필요 없습니다** —— Python 표준 라이브러리만 씁니다.

### 3. 화면 열기

브라우저에서 <http://127.0.0.1:8650> 접속.

첫 실행 시 자동으로 한 사이클 수집합니다(약 3~5분). 이후 설정한 간격으로 반복합니다.

## 기본 필터 규칙

수집되는 게시물은 많지만 **정말 볼 만한 건 극소수**입니다. 그래서 화면에는 세 개의 문이 기본으로 켜져 있습니다:

| 규칙 | 기본값 | 설명 |
|---|---|---|
| 관련만 | ✅ 켜짐 | 본문이 키워드에 매칭 (아래 「관련성 필터」 참조) |
| 이미지 있는 것만 | ✅ 켜짐 | **텍스트만 있는 게시물은 숨김** —— 시각적 참고 가치가 없음 |
| 최소 인터랙션 | **30** | 좋아요 / 답글 / 리포스트 **셋 중 하나라도** 임계값 초과 |

「최소 인터랙션」은 **셋 중 최댓값**으로 판정하며 합계가 아닙니다 —— 합계로 하면 「좋아요 34 + 답글 33 + 리포스트 33」과 「좋아요 100 + 0 + 0」이 같은 등급이 되지만, 터진 건 후자뿐입니다. 인용은 판정에서 제외합니다(인용은 「언급되어 논의되는 정도」이지 게시물 자체의 추진력이 아니기 때문).

**세 스위치 모두 화면에 있고 언제든 꺼서 전체를 볼 수 있습니다.** 임계값은 `.env`에 고정할 수도 있습니다:

```ini
RADAR_MIN_INTERACTIONS=30
```

## 어떻게 데이터를 가져오나

### 핵심: Googlebot UA + 서버 사이드 렌더링

Threads는 일반 브라우저 UA에 **콘텐츠를 서버 사이드 렌더링하지 않습니다** —— 약 275 KB의 빈 껍데기만 돌려주고 내용은 전부 JS로 불러옵니다.

하지만 **Googlebot UA**로 바꾸면 Meta가 완전한 SSR 페이지(1~2 MB)를 순순히 돌려주고, 게시물 데이터가 인라인 JSON으로 들어 있습니다.

그래서 이런 파이프라인이 성립합니다:

```
Googlebot UA로 검색 페이지 요청
  → SSR HTML 수신
  → <script type="application/json"> 에서 JSON 추출
  → 게시물 객체 재귀 탐색
  → 필드 정규화
```

**로그인 불필요, OAuth 불필요, App Review 불필요.**

### ⚠️ 코드를 고칠 때 가장 많이 밟는 함정: 필드 위치

네 개의 지표는 **같은 층에 없습니다**:

| 필드 | 위치 |
|---|---|
| `like_count` | 게시물 객체 **최상위** |
| `direct_reply_count` | `text_post_app_info` 안 (**`reply_count`가 아님**) |
| `repost_count` | `text_post_app_info` 안 |
| `quote_count` | `text_post_app_info` 안 |

따라서 「이게 게시물 객체인가」 판정 조건은 `code` + `like_count` + `text_post_app_info` **셋 다**여야 합니다. 앞의 둘만 보면 바깥 층에서 멈춰 나머지 셋이 전부 0으로 읽힙니다.

또한 `has_image`를 `bool(raw.get("image_versions2"))`로 쓰면 **안 됩니다** —— Threads는 **모든** 게시물(텍스트 전용 포함)에 이 키를 돌려주고, 텍스트 전용일 때 값은 빈 껍데기 `{"candidates": []}`입니다. 그 불리언은 항상 True가 됩니다(실측으로 겪음: DB의 약 2만 건이 전부 이미지 있음으로 잘못 기록됨).

## 키워드 작성법

프로젝트 루트의 `keywords.txt`를 편집하거나 화면에서 추가·삭제합니다(화면에서 바꾼 내용은 같은 파일에 기록됩니다).

```
# 한 줄에 키워드 하나, [대괄호]는 그룹

[모델]
ChatGPT | GPT | chatgpt
Claude | ClaudeAI | Anthropic Claude

[이미지 생성]
Midjourney | midjourney
AI art | AI 绘画 | AI画
```

세 가지 규칙:

- **`|`는 동의어** —— 검색에는 **첫 번째** 표기만 쓰지만, 본문이 어느 것이든 매칭되면 관련으로 봅니다. 정확도를 해치지 않고 재현율을 보충합니다(「GPT」라고만 쓰고 정식 명칭을 안 쓰는 글이 아주 많습니다).
- **공백은 AND** —— `AI prompt`는 「AI」와 「prompt」가 모두 필요합니다. 붙여 쓴 형태도 매칭됩니다(`#aiprompt`).
- **`[그룹]`** 은 화면 분류용일 뿐이고 언제든 바꿀 수 있습니다. 그룹 이름은 **다른 언어로 번역되지 않습니다** —— 데이터 값이기도 해서, 번역하면 화면의 단어로 파일을 검색할 수 없게 되기 때문입니다.

## 관련성 필터

Threads 검색은 「그 단어가 들어간 글」이 아니라 **의미적으로 관련된** 결과를 돌려줍니다. 실측으로 「AI prompt」를 검색하면 인도네시아어·말레이어 어그로 글이 나오고, AI 규제를 논하는 정치인 게시물(1만 좋아요로 1위)까지 나옵니다. AI와 살짝 닿아 있지만 주제 선정에는 전혀 쓸모가 없습니다.

그래서 필터 층을 둡니다. 순수 키워드 규칙이고 모델을 부르지 않습니다:

| 판정 | 조건 |
|---|---|
| `blocked` | `blocklist.txt`의 단어에 매칭 → 즉시 제외 |
| `relevant` | 본문이 키워드에 매칭(구 전체, 또는 모든 토큰, 또는 붙여 쓴 형태) |
| `offtopic` | 나머지(검색에는 걸렸지만 키워드와 무관) |

구현상 두 가지:

1. **`ai` 같은 짧은 단어는 부분 일치로 오탐합니다** —— `said` / `again` / `available`. 그래서 순수 ASCII 단어는 간이 단어 경계 일치(앞뒤에 영숫자 불가)를 씁니다.
2. **`tag` 필드도 매칭에 참여합니다** —— 「AI Threads」 커뮤니티에 속한 글은 tag에서 「AI」를 공급합니다. 즉 본문에 「prompt」만 있어도 키워드 `AI prompt`에 매칭됩니다.

**「키워드 매칭 필수」는 이 방식의 숙명입니다**: 「ChatGPT Images 2.5 能給我們設計師留一條生路?」처럼 명백히 AI 관련이어도 키워드 목록에 없는 단어라면 offtopic이 됩니다. **해법은 `keywords.txt`에 단어를 추가하는 것이지 규칙을 느슨하게 하는 게 아닙니다** —— 느슨하게 하면 즉시 노이즈가 쏟아집니다.

### 인터랙션 0인 게시물은 저장하지 않음

Threads는 검색 결과 한 페이지를 채우려고 **막 올라온, 반응이 전혀 없는** 글을 대량으로 돌려줍니다. 실측으로 어느 사이클에서 1,421건을 받아 관련이 359건뿐이었고, 나머지는 거의 전부 좋아요 0의 무관한 노이즈였습니다.

그래서 수집 층에 문을 하나 둡니다: **네 지표가 모두 0인 게시물은 DB에 쓰지 않습니다**.

이건 「영구 폐기」가 아니라 **지연 수집**입니다 —— 다음에 다시 수집될 때 반응이 생겼다면 정상적으로 저장됩니다. 잃는 건 「반응 0이던 구간」의 성장 궤적뿐이고, 게시물 자체를 잃는 게 아닙니다.

> 이 규칙은 「인터랙션이 특정 값 미만이면 수집하지 않음」보다 훨씬 온건합니다: 후자는 이미 출발해서 오르고 있는 글까지 막아버립니다.

## 수집 변형과 차단 위험

같은 검색어라도 `serp_type` 파라미터를 바꾸면 **다른 배치**가 돌아옵니다. 사실상 페이지 넘김입니다.

실측 변형 간 중복은 **50~63%**뿐입니다:

| 쿼리 | base | recent | profile | 셋의 합집합 |
|---|---|---|---|---|
| `q=Claude` | 76건 | 74건 | 74건 | **137건 (+80%)** |
| `q=ChatGPT` | 61건 | 60건 | 62건 | **109건 (+79%)** |

그래서 변형을 늘리는 게 재현율을 올리는 가장 직접적인 수단입니다:

```ini
RADAR_SERP_TYPES=base,profile,recent
```

사용 가능한 값: `base`(파라미터 없음), `recent`, `top`, `tag`, `profile`, `default`.

### ⚠️ 변형 수가 차단 위험을 직접 좌우합니다

**이 프로젝트에서 가장 절제해야 할 파라미터입니다.** 실측:

| 구성 | 요청 수 | 결과 |
|---|---|---|
| 변형 3 × 키워드 19 | 사이클당 57회 (약 114/시간) | **3사이클 연속 후 threads.com이 502 반환**, 약 20분 뒤 자가 회복 |
| 변형 2 × 키워드 19 | 사이클당 38회 | 안정 |
| 변형 3 × 키워드 12 | 사이클당 36회 (약 72/시간) | 안정 (현재 기본값) |

**권장**: `키워드 수 × 변형 수 ≤ 40`을 지키고 간격은 30분 이상으로. 한 번 제한되면 **부하를 낮추고 한동안 쉬는 것만이 유일하게 효과 있는 회복책**입니다. 무리한 재시도는 차단을 연장시킬 뿐입니다.

차단 여부 진단: `threads.com`과 무관한 사이트(예: `baidu.com`)를 동시에 테스트하세요. threads만 실패 → 출구 IP가 Meta에 제한됨. 둘 다 실패 → 프록시가 죽음.

## 실시간 모니터링 동작 방식

서비스 안의 백그라운드 스레드가 설정 간격으로 수집을 반복합니다. 주 경로 외에 네 겹의 안전장치가 있습니다:

- **채널 자가 진단** —— 현재 프록시 경로가 아직 SSR 페이지를 받을 수 있는지 원클릭으로 확인해, 「수집기 고장」과 「출구 차단」을 구분합니다
- **서킷 브레이커** —— 「한 사이클 완전 무수확」이 3회 연속이면 자동 일시정지. 사이클 전체가 0이면 채널급 장애이고, 간격대로 재시도해봐야 차단만 깊어집니다
- **사이클 전체 워치독** —— 노트북 절전이 수집 스레드를 통째로 얼립니다(실측: 15.5시간 동안 응답 없음). 그래서 사이클 단위 타임아웃을 보험으로 둡니다
- **중단된 실행 정리** —— 프로세스가 강제 종료된 뒤 DB에 `running`으로 남은 실행은 자동으로 중단으로 표시됩니다

## 설정

모든 설정에 기본값이 있고, 프로젝트 루트의 `.env`에 적으면 덮어씁니다(전체 목록은 `.env.example` 참고).

```ini
RADAR_PORT=8650                        # 서비스 포트
RADAR_INTERVAL_MINUTES=30              # 수집 간격(분)
RADAR_SERP_TYPES=base,profile,recent   # 수집 변형: 많을수록 넓지만 위험도 큼
RADAR_MIN_INTERACTIONS=30              # 「최소 인터랙션」 슬라이더 초기값
RADAR_CYCLE_MAX_SECONDS=1800           # 사이클 시간 상한(워치독)
RADAR_FAILURE_LIMIT=3                  # 무수확이 몇 사이클 이어지면 차단할지
RADAR_HOST=127.0.0.1                   # 바인드 주소, 기본은 로컬 전용
```

화면에서 수집 간격을 바꾸면 **`.env`에 다시 기록**되므로 재시작해도 설정이 사라지지 않습니다.

### HTTP 인터페이스

다른 도구와 연동할 수 있게 JSON 인터페이스도 제공합니다:

| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | `/api/status` | 실행 상태, 통계, 최근 로그 |
| GET | `/api/posts?limit=&only_relevant=` | 게시물 목록 |
| GET | `/api/authors?limit=&tier=` | 계정 집계 순위 |
| GET | `/api/post/<code>` | 단일 게시물 상세 |
| GET | `/api/stream` | SSE 이벤트 스트림 |
| GET | `/api/export?what=posts\|authors` | CSV 내보내기(UTF-8 BOM, Excel에서 바로 열림) |
| POST | `/api/collect` | 즉시 한 사이클 수집 |
| POST | `/api/pause` `/api/resume` | 일시정지 / 재개 |
| POST/DELETE | `/api/keywords` `/api/watchlist` | 키워드와 관심 목록 추가·삭제 |

## 자주 묻는 질문

**Q: 실행 후 계속 로딩만 되거나 0건?**
화면의 「자가 진단」 버튼을 누르세요. DNS, 프록시 터널, UA 강등, 속도 제한 중 어디서 막혔는지 명확히 알려줍니다.

**Q: 목록 건수가 「DB 내 N건」보다 훨씬 적은 이유?**
설계상 그렇습니다. DB 내는 수집한 전체량이고, 목록은 기본으로 「관련 + 이미지 있음 + 인터랙션 달성」 부분만 보여줍니다. 스위치를 끄면 전체를 볼 수 있습니다.

**Q: 상승 속도 열이 전부 0인 이유?**
속도는 **앞뒤 두 번 수집의 반응 증가분**을 비교해 계산합니다. DB를 비운 직후나 막 시작했을 때는 게시물마다 스냅샷이 하나뿐이라 2사이클 이상 쌓여야 계산됩니다.

**Q: 중국어가 깨져 보입니다**
CSV 내보내기는 UTF-8 BOM을 쓰므로 Excel에서 바로 열어도 안 깨집니다. 다른 곳에서 깨진다면 터미널 인코딩을 확인하세요(Windows는 `chcp 65001`).

**Q: 서버에 올려 상시 운영할 수 있나요?**
가능하지만 두 가지 주의: ① `RADAR_HOST` 기본값은 `127.0.0.1`(로컬 전용)이고, 외부 공개하려면 `0.0.0.0`으로 바꾸고 **직접 리버스 프록시와 인증을 붙여야 합니다** —— 이 프로젝트엔 사용자 시스템이 없습니다. ② 출구 IP가 차단 확률을 좌우하며, 데이터센터 IP는 보통 가정용보다 더 잘 막힙니다.

## 알려진 한계

버그가 아니라 이 방식의 경계입니다. 헛수고를 막기 위해 적어둡니다:

1. **검색 재현율에는 상한이 있고 커버리지는 100%가 될 수 없습니다.** 쿼리당 한 페이지(약 50~80건)만 돌아오고, 커뮤니티(예: 「AI Art」) 안의 막 올라온 반응 0 게시물은 후보 집합에 못 듭니다. 실측으로 게시물의 도입 문구 그대로 검색해도 **0건** —— Threads 검색은 **전문 인덱스가 아니라** 알고리즘 후보 집합입니다.
2. **커뮤니티 페이지는 가져올 수 없습니다.** 브라우저에서 보이는 「토픽 커뮤니티 페이지」(인기/최신 탭)는 JS 렌더링이라 헤드리스 SSR로는 퇴화된 결과만 나옵니다(실측: 무관한 글만 반환). 이를 커버하려면 JS 렌더링 + 로그인 세션이 필요하고, 이 프로젝트의 「의존성 0, 로그인 없음」과 정면으로 충돌합니다.
3. **막 올라온 콘텐츠는 노이즈 투성이입니다.** 실측으로 어느 사이클의 신규 수집 게시물 관련율은 **1.5%**뿐(기존 게시물은 34~59%). 「실시간」과 「관련성」은 본질적으로 상충하며, 「반응 0은 저장 안 함」으로 대부분 걷어냈습니다.
4. **인터랙션이 대량으로 0인 건 정상입니다.** 롱테일이 대다수이고, 그래서 「최소 인터랙션」 슬라이더가 있습니다.
5. **Threads의 페이지 구조에 의존합니다.** Meta가 SSR 데이터 구성을 바꾸면 파싱 로직도 따라가야 합니다. `collector.py` 상단 주석에 필드 위치를 적어두었으니 고치는 건 어렵지 않습니다.
6. **단일 머신, 단일 프로세스, 인증 없음.** 내 PC에 상주시키는 개인 도구이며 다중 사용자 서비스가 아닙니다.

## 파일 구성

```
threads-ai-radar/
├── server.py          HTTP 서비스 + JSON API + 정적 파일
├── monitor.py         백그라운드 스케줄링: 주기 수집, 자가 진단, 서킷 브레이커, 워치독
├── pipeline.py        한 사이클 구성: 수집 → 관련성 판정 → 점수 → 저장
├── collector.py       수집 층: Googlebot UA로 SSR 페이지를 받아 인라인 JSON 파싱
├── relevance.py       관련성 판정: 순수 키워드 규칙(blocked / relevant / offtopic)
├── scorer.py          바이럴 점수와 상승 속도
├── store.py           SQLite 저장: 스키마, 마이그레이션, 쿼리, 계정 집계
├── config.py          설정 로딩(.env와 환경 변수)
├── selftest.py        자가 진단: 필터와 순위를 돌려 제외된 샘플을 출력
├── refilter.py        키워드 수정 후 기존 데이터 재필터(재수집 불필요)
├── start.bat          Windows 원클릭 실행
├── requirements.txt   비어 있음 —— 이 프로젝트는 서드파티 의존성 0
├── keywords.txt       모니터링 키워드(화면에서 편집 가능, 이 파일에 기록됨)
├── blocklist.txt      차단어(매칭되면 즉시 제외)
├── watchlist.txt      관심 계정
├── .env.example       설정 예시
├── data/
│   └── radar.db       SQLite 데이터베이스(샘플 데이터 동봉, 바로 화면 확인 가능)
├── docs/              이 README에 쓰인 스크린샷
└── web/
    ├── index.html     단일 파일 프런트엔드(프레임워크 없음, 빌드 없음)
    └── i18n.js        5개 언어 사전과 런타임(중국어 간체 / 영 / 번체 / 일 / 한)
```

**UI는 5개 언어를 지원합니다**: 简体中文, English, 繁體中文, 日本語, 한국어. 오른쪽 위에서 전환하고 선택은 localStorage에 저장됩니다. UI 문구는 전부 번역하지만 **게시물 본문, 계정 이름, 그룹 이름은 번역하지 않습니다** —— 그건 데이터이지 인터페이스가 아닙니다.
